# 共享提交积压准入

本页定义 P1 的训练队列。用户于2026-11-03明确采用以下训练口径：同一用户跨训练场景统计 `queued`＋`running`，每份提交计一次；终态释放，超额只拒绝新增，同键重试保留原语义。存储层按同一主体跨上下文实现该计数；全局覆盖全部主体、上下文和材料版本。具体限额要求显式配置，不预设生产值，试用阈值仍待确认。[训练虚拟时间](#训练虚拟时间)用于领取排序；提交频率、团队/比赛额度和真实账号训练权限另行交付。

## 策略与接口

schema 6 增加单行 `submission_backlog_policy`，全局/主体额度须为正 int64，主体不超过全局。迁移和固定材料夹具均不创建策略；仅受信维护命令 `migrate backlog <global> <subject>` 原子更新两项额度。API 不初始化或修复策略，不从各副本环境变量取得独立额度，也不提供公开管理接口。重复配置以数据库最后成功提交为准，与正在接收的事务协调；降低额度保留所有已接受任务，只拒绝超额的新提交。

schema9另有[持久化参考验证申请](reference-requests.md)的独立queued额度及默认空policy，本页判题积压配置不启用它。两套额度不等于共享Worker/沙箱容量；参考申请当前没有消费者，后续共享容量与受权执行仍待接通。

| 情况 | POST 行为 |
| --- | --- |
| 同归属、原键和相同内容已接受 | 返回原回执，满额或缺策略时仍可恢复 |
| 同归属、原键但不同内容 | `409 IDEMPOTENCY_CONFLICT`，不覆盖原任务 |
| 全局或主体额度已满 | `429 BACKLOG_LIMIT`，本次不新建提交/任务 |
| 策略未配置 | `503 ADMISSION_UNAVAILABLE`，本次不新建提交/任务 |
| 数据库、锁等待取消或提交结果未知 | 保留原错误分类，HTTP 为 `503 ACCEPTANCE_UNKNOWN`，不能推断事务回滚 |

数据响应 `no-store`；没有可保证的释放时间，不附 `Retry-After`。已知拒绝也不能否认先前未知请求可能已提交，客户端继续保留原键核验；浏览器不自动换键或将既有结果归为当前未核验内容。GET 回执不消耗额度、不证明当前源码绑定。固定 Bearer 和浏览器接口仍仅为隔离实验。

## 原子性与计数

`Store.Accept` 使用 READ COMMITTED、有界事务：先读原回执，再锁共享策略行；取得锁后用**独立 SQL 语句**重新读原回执，随后检查材料，再以另一条语句计数，最后同事务写提交和任务。锁等待结束后的新语句获得新快照，避免用锁前快照错拒同键重试或放行最后一个名额。所有新提交经过同一行锁，简化跨 API 的最后名额竞争，代价是数据库级接收串行化及最多五秒的事务预算；这不是已验证的生产吞吐能力。

权威计数来自 `judge_tasks` 连接 `submissions`，没有需要补偿的冗余计数器。queued→running、失联重排和可重试 SE 保持占用；finished 或耗尽尝试的 failed 才释放，failed 无选手判定。重复/旧回报不重复释放。当前其他状态转换只保持或减少积压，因此不需拿准入锁；未来引入重判或任何终态→queued 路径时，必须协调此准入事务，不能直接恢复占用。

`CountBacklog` 先筛选**全部** queued/running（不先按主体/场景过滤），再以全局上限截断，物化后计全局与主体数。窗口已满即可拒绝全局；未满则全量未终结集合已包含，主体数准确。无排序要求，不依赖截断顺序。部分索引 `judge_tasks_unfinished(submission_id)` 避免将历史终态全部作为候选；queued/running 插入与跨终态转换增加索引写入、WAL、存储及 vacuum 成本，不承诺 LIMIT 能固定扫描工作量，仍受可见性、死元组和连接计划影响。

真实 PostgreSQL 测试在 2048 份终态、3 份未终结数据上，对权威 SQL 使用未强制 planner 的 `EXPLAIN ANALYZE / BUFFERS`，实际选用该部分索引。该小数据查询计划只是等价验证，不代表大规模积压、目标硬件或首批100人容量验收。

## 个人训练提交事务

普通训练的存储入口先按恢复代次、账号、邮箱的顺序锁定当前训练资格，再进共享积压与材料版本队列。账号 ID 来自新的普通会话读取；训练上下文固定为本人训练，材料版本由服务端选择。重试仍须验证当前资格，只有原键与原内容相同才复用已提交回执。读回执用同一身份检查，但不占队列配额，也不要求当前材料可用。原键查不到不能排除仍在执行的写入。

浏览器入口默认关闭；本机验收仅接受本地发布且与当前显式配置的执行准入绑定的版本。A+B 与并查集分别使用自己的清单和队列。浏览器请求键还绑定题目和显示版本；回执查找不依赖当前发布。生产提交未开放。沿用现有索引，无迁移；固定 M0 入口保留原行为。

## 训练虚拟时间

固定材料 Store 按材料版本维护虚拟时钟，按主体跨训练上下文分配顺位。每次新提交取“该版本已经领取的最大顺位”和“该主体在该版本仍排队的最大顺位”两者中的较大值，再加一。同一顺位按入队序号先后领取。例如，A 先提交六次，B 后提交一次，空队列起步时领取顺序为 A1、B1、A2…A6。虚拟顺位不改接收时间、判定、罚时或排名，也不衡量 CPU 时间。

接收事务按准入策略→版本时钟写入提交及任务；领取事务按节点→版本时钟→任务建立尝试、更新时钟并一起提交。等待版本时钟后另起查询获取新快照；暂时锁住队首时不跳过，领取仍受五秒事务预算限制。空队列、无节点容量和回滚均不推进时钟；原键回执不分配新顺位。SE 或失联重排保留顺位和入队序号，不取时钟锁；如果重排在本次候选快照后提交，由下一次领取重新比较。顺位只决定领取，不保证完成顺序。

`judge_tasks_training_queue` 按版本和顺位索引排队任务，接收计算只需要同版本排队集合及同主体匹配；两条查询都核对提交的材料版本。新索引在入队、领取、重排时增加写入和 WAL，仅存仍排队的条目；任务排序字段随回执保留，旧终态不回填。版本时钟增加同版本接收与领取的串行区间；不同版本各有时钟，提交仍共享全局准入锁。该范围不包含跨版本调度、比赛优先、真实身份或试用容量验收。

## 升级与回退

schema 23 的本人提交历史索引按主体、训练范围、接收时间和提交 ID 查找，每页最多 20 条，时间相同也不会丢项。每页独立读取；新增和状态变化须刷新第一页。索引避免随历史累积反复排序，每次接收新增一个 B-tree 条目及相应 WAL，升级要预留构建空间和维护窗口。Down23 仅移除索引。

普通会话可显式启用[本人训练提交历史](../api/training-history.openapi.yaml)。每页以实际会话身份和固定 `personal-training` 范围过滤，在短事务中先锁定并复核[训练账号资格](architecture/session-design.md#125-训练账号资格)，再用已有索引读取。客户端传入的预期主体与游标均不授予权限。摘要不含源码、幂等键、题面或逐点详情。关闭配置项即关闭路由，保留已有历史与索引。

独立开关 `training_submission_detail` 默认关闭。开启后单条详情在同样的资格事务内按提交主键、实际主体和固定范围读取，统一将不存在、他人或其他范围返回为 404。响应只含原源码及当前回执，浏览器显式读取并在翻页、切换账号或页面失效时清除。Worker 只持久化判定和证据摘要，详情不展示逐点结果或内部证据。无新迁移；关闭该开关即可停止详情读取，历史列表可独立保留。

1. 停止全部 API、Worker、恢复进程和材料登记等维护写入，确认活动事务退出；启动版本检查不会终止已运行的进程，**不支持滚动混用**。

## 训练准入负载采样

手动 `toolchain training-load` 以 Unix socket 启动独立临时 PostgreSQL，使用新库中的两个实际 Store 和一个合成领取方。每轮先为密集主体跨上下文提交 32 份，核对主体超额和跨 Store 原键回执；再以最多 16 路并发为另外 99 个主体提交，核对全局 128 份上限与剩余 96 个名额。随后并行注入第二轮提交和单领取方，每份领取后等待 12 毫秒再合成回报；接收数量随调度变化。核对首次接收的低频主体先于密集主体第二份、同主体顺序和所有已接受提交恰有一次完成尝试。

三轮分别报告接受／拒绝数量和 Store 调用耗时，以及从数据库 `created_at` 到同容器领取返回的等待；耗时输出 p50、p95 和最大值，不设生产通过线。该采样刻意复现饱和队列，适合区分数据库行为与后续混合负载结果。普通 `toolchain db` 保留原测试范围。这里不启动 API、Redis 或真实 Worker，不包含公网、真实判题与登录；本地资源上限可参考试用机规格，100 人在线和试用部署容量另行验收。
