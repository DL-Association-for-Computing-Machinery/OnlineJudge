# 共享提交积压准入

本页定义 P1 的积压子项。用户于2026-11-03明确采用以下训练口径：同一用户跨训练场景统计 `queued`＋`running`，每份提交计一次；终态释放，超额只拒绝新增，同键重试保留原语义。存储层按同一主体跨上下文实现该计数；全局覆盖全部主体、上下文和材料版本。具体限额要求显式配置，不预设生产值，试用阈值仍待确认。频率限流、团队/比赛额度、DOMjudge 虚拟时间公平调度和真实账号训练权限另行交付。

## 策略与接口

schema 6 增加单行 `submission_backlog_policy`，全局/主体额度须为正 int64，主体不超过全局。迁移和固定材料夹具均不创建策略；仅受信维护命令 `migrate backlog <global> <subject>` 原子更新两项额度。API 不初始化或修复策略，不从各副本环境变量取得独立额度，也不提供公开管理接口。重复配置以数据库最后成功提交为准，与正在接收的事务协调；降低额度保留所有已接受任务，只拒绝超额的新提交。

schema9另有[持久化参考验证申请](reference-requests.md)的独立queued额度及默认空policy，本页判题积压配置不启用它。两套额度不等于共享Worker/沙箱容量；参考申请当前没有消费者，后续共享容量与受权执行仍待接通。

| 情况 | POST 行为 |
| --- | --- |
| 同归属、原键和相同内容已接受 | 返回原回执，满额或缺策略时仍可恢复 |
| 同归属、原键但不同内容 | `409 IDEMPOTENCY_CONFLICT`，不覆盖原任务 |
| 全局或主体额度已满 | `429 BACKLOG_LIMIT`，本次不新建提交/任务 |
| 策略未配置 | `503 ADMISSION_UNAVAILABLE`，本次不新建提交/任务 |
| 数据库、锁等待取消或提交结果未知 | 保留原错误分类，HTTP 为 `503 ACCEPTANCE_UNKNOWN`，不能推断事务回滚 |

数据响应 `no-store`；没有可保证的释放时间，不附 `Retry-After`。已知拒绝也不能否认先前未知请求可能已提交，客户端继续保留原键核验；浏览器不自动换键或将既有结果归为当前未核验内容。GET 回执不消耗额度、不证明当前源码绑定。固定 Bearer 和浏览器接口仍仅为隔离实验。

## 原子性与计数

`Store.Accept` 使用 READ COMMITTED、有界事务：先读原回执，再锁共享策略行；取得锁后用**独立 SQL 语句**重新读原回执，随后检查材料，再以另一条语句计数，最后同事务写提交和任务。锁等待结束后的新语句获得新快照，避免用锁前快照错拒同键重试或放行最后一个名额。所有新提交经过同一行锁，简化跨 API 的最后名额竞争，代价是数据库级接收串行化及最多五秒的事务预算；这不是已验证的生产吞吐能力。

权威计数来自 `judge_tasks` 连接 `submissions`，没有需要补偿的冗余计数器。queued→running、失联重排和可重试 SE 保持占用；finished 或耗尽尝试的 failed 才释放，failed 无选手判定。重复/旧回报不重复释放。当前其他状态转换只保持或减少积压，因此不需拿准入锁；未来引入重判或任何终态→queued 路径时，必须协调此准入事务，不能直接恢复占用。

`CountBacklog` 先筛选**全部** queued/running（不先按主体/场景过滤），再以全局上限截断，物化后计全局与主体数。窗口已满即可拒绝全局；未满则全量未终结集合已包含，主体数准确。无排序要求，不依赖截断顺序。部分索引 `judge_tasks_unfinished(submission_id)` 避免将历史终态全部作为候选；queued/running 插入与跨终态转换增加索引写入、WAL、存储及 vacuum 成本，不承诺 LIMIT 能固定扫描工作量，仍受可见性、死元组和连接计划影响。

真实 PostgreSQL 测试在 2048 份终态、3 份未终结数据上，对权威 SQL 使用未强制 planner 的 `EXPLAIN ANALYZE / BUFFERS`，实际选用该部分索引。该小数据查询计划只是等价验证，不代表大规模积压、目标硬件或首批100人容量验收。

## 升级与回退

1. 停止全部旧版写入 API，并确认在途接收结束；启动模式检查不能阻止已运行旧二进制绕过新准入，**不支持新旧写入 API 滚动混用**。
2. 通过独立维护流程执行 `migrate up` 到当前 schema 14（本页积压能力始于6，[私有草稿](problem-drafts.md#私有草稿入库与本人读取)始于7，列表索引始于8，[参考申请](reference-requests.md)始于9）；索引为普通事务索引，维护窗口须考虑建索引及锁等待。固定实验若需初始化材料，再执行 `migrate fixture`，材料版本与各进程一致。
3. 显式执行 `migrate backlog <global> <subject>`，检查配置成功后启动同版本 API。无生产默认数值；专项临时库的 `10000 10000` 只为合成夹具。
4. 已有积压超过新额度时不迁移或删除任务，等待正常完成后再接受新提交。管理员更新策略也等待在途准入释放同一策略锁。

上述命令使用 Docker 构建的 `.local/bin/migrate` 和私有 `OJ_DATABASE_URL`；维护凭据不下放 Worker 或浏览器。当前二进制只接受 schema 14，启动检查不自动迁移。Down14 仅允许无对拍计划时回退；Down13 仅允许空领取历史回退；Down12 仅允许空报告与终态回退；Down11 仅允许空预留表回退；Down10 仅允许空计划表回退；Down9 仅在参考申请历史及其policy均为空时允许，已配置、queued或cancelled均拒绝，精确合同见[参考申请回退](reference-requests.md#迁移与回退)。schema8仅索引的回退和schema7数据保护条件见[草稿合同](problem-drafts.md#入库版本与迁移)；schema6的 Down 继续在与接收一致的表锁顺序下，仅允许**没有任何提交且没有策略行**的空库回退；已配置或已接受数据须向前修复，不通过清表或删除策略绕过保护。更换schema时须排空/停止旧API、Worker及维护写入，不因仅停止写入API就混跑版本；停用浏览器页面不会取消已接受工作。本次没有迁移现有持久化localdev或部署服务器。
