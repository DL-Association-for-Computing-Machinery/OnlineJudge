# ADR-001：Go + Gin 自研与成熟组件复用边界

初始决策日期：2026-10-25。以下选型理由及未实现措辞记录当时背景；当前引入、验证和缺口见 [M0 记录](../m0-experiment.md)与 [README](../../README.md)。原始状态：Go + Gin 自研、模块化单体＋独立判题 Worker 和 React＋TypeScript＋Vite 前端已由用户确认；已有 API/Worker/前端工程骨架，业务细化设计尚未实现或压测；精简阶段见 [交付基线](../phase-1-development-plan.md)。文档修订以 Git 历史为准。

## 决策来源与背景

用户明确要求：“我希望你参考它们的思路，但是项目是我自己用go+gin去写”。本决策替代此前“以 Hydro 为基础进行二次开发”的建议；此前建议不是用户已批准的实现路线。

主要开发者为用户与 AI，未来可能增加长期维护者。需求包含长期战队、赛事阵容、题目审核、成长体系与名额管理，具体见 [需求文档](../requirements.md)。这些模型应由本项目掌握，不能被上游 OJ 的数据结构隐式限制。

## 已确认方向

1. 后端使用 Go + Gin 自研；Hydro 和 DOMjudge 作为业务与工程参考。
2. 可以安装 Linux；Docker 是否可用仍待现场核验。
3. 复用成熟基础能力的原则保留；优先验证 PostgreSQL＋持久化任务表和 go-judge，尚未正式采用或锁定具体第三方依赖。
4. AI 参与实现、验证和文档维护；产品决策、代码合并和生产发布责任由人承担。
5. 用户确认先采用模块化单体＋独立判题 Worker，硬件信息后续补充；不将该决定等同于全部细化方案已批准或容量已验证。
6. 前端采用 React＋TypeScript＋Vite，样式与组件使用 Tailwind CSS＋shadcn/ui，代码编辑器使用 CodeMirror 6，首期代码草稿仅保存在浏览器本地，按静态资源＋Go API 设计；选型依据、备选与代价见 [前端与沙箱选型](frontend-sandbox-options.md)。配套已确认 React Router（声明式）＋TanStack Query＋fetch＋pnpm 及前端设计第 3.1 节约定；本地草稿采用 IndexedDB＋idb，保存/恢复/冲突/清理规则见前端设计第 3.2 节；题面采用 react-markdown＋remark-gfm＋remark-math＋rehype-katex／KaTeX，渲染约定见前端设计第 3.3 节；容量预算、其他配套及具体版本待定。
7. 首期数据库保存小数据、校内本地磁盘保存大文件、Worker 使用可重建本地缓存，预留对象存储迁移接口；数据归属、拓扑限制及验收见 [存储设计](storage-design.md)。不等于存储已具备主机高可用。
8. 首批工具链采用 GCC 15：C 使用 C17，C++ 默认 GNU++17、可选 GNU++20；Java 使用 Temurin JDK 21，Python 使用 CPython 3.14；PyPy 后续评估。补丁版本、构建环境、命令模板、资源限制与兼容性仍需验证，配置边界见 [前端与沙箱选型](frontend-sandbox-options.md#61-首批工具链与语言标准)。
9. 数据库访问层优先验证 sqlc＋pgx：SQL 与事务明确可审查，sqlc 生成调用代码，pgx 承担连接与执行。正式采用及依赖版本待验证；GORM 保留为备选，见 [总体架构](system-design.md#81-数据库访问层验证路线)。
10. 数据库迁移采用 Goose＋SQL 迁移文件＋独立迁移步骤＋显式迁移锁；不随各 API 副本启动自动改表。版本、锁配置、事务与恢复须实测，详见 [迁移设计](system-design.md#811-数据库迁移)。本决定不等同于已安装、已执行迁移或 PostgreSQL 已通过准入。
11. 登录采用服务端 Session＋Redis 共享会话＋HttpOnly Cookie，替代此前“会话存 PostgreSQL、暂不引入 Redis”的建议；账号与权限仍按关系数据库路线管理。Redis 不接管判题持久化队列，细节与故障边界见 [会话设计](session-design.md)。
12. 用户确认分场景期限初值：普通空闲 2 小时/最长 12 小时，主动保持登录 24 小时/7 天，管理后台 30 分钟/8 小时并对敏感操作再次验证；普通最多 3 个会话，正式线下比赛按参赛主体仅 1 个有效参赛会话，拒绝第二次登录、由工作人员协助换机。每场线下团队赛使用独立队伍账号，比赛结束停止提交，赛后查看窗口默认 30 分钟后停用；详细边界见 [会话与账号规则](session-design.md#21-分场景有效期)。

## 设计基线

密码保存已确认 Argon2id＋每个密码独立随机盐＋可升级参数记录；具体参数等硬件确定后验证，未确认 Go 封装或精确版本。记录解析、并发升级/重置与计算资源预算见 [密码设计](session-design.md#7-密码保存与校验)。

账号流程已确认日常邮箱验证注册＋密码登录＋邮箱自助找回，正式比赛校内发号＋人工核验重置。邮件依赖限制在日常激活/找回，既有登录和正式比赛核心链路须校内独立运行；可替换 SMTP 接口已确认、go-mail 优先验证；供应商及域名条件待定，见 [账号流程与邮件选型](session-design.md#8-注册找回与账号发放)。

会话库验证顺序补充：用户确认优先验证 SCS＋go-redis，保留 Gin sessions 为备选。正式采用和版本待验证，不安装两套会话实现或用候选库默认行为降低既有规则；边界与验证出口见 [会话库验证路线](session-design.md#6-会话库与-redis-客户端验证路线)。

- 一个仓库管理应用、判题 Worker、前端和部署资料；目录在首个实现任务中确定。
- 业务采用模块化单体：身份权限、战队训练、题库出题、比赛、榜单、赛务、外部同步、成长和名额模块各自拥有数据与规则。
- Gin 接口层负责输入校验、身份上下文和响应转换；应用层编排用例；领域层承载规则；持久化、沙箱和第三方服务放在适配层。
- 核心业务不导入 Gin、数据库驱动或供应商 SDK。跨模块通过公开接口协作，不直接修改对方私有表或集合。
- 判题 Worker 独立进程、独立运行环境，可部署到多台主机；业务服务不直接运行选手代码。
- 提交接收、任务持久化、领取确认、超时恢复和结果去重必须形成完整协议；不提前承诺消息队列能够提供“恰好一次”。
- 比赛成绩以可追溯提交和判题结果为依据；重判需要纠正榜单、气球、成长等派生数据。旧尝试回调不能覆盖新重判结果。
- 正式比赛资源与 AI 造数据、训练任务设置隔离或明确调度优先级；不可依赖外部 AI 实时可用。

## 复用边界

| 能力 | 本项目责任 | 可复用候选与限制 |
| --- | --- | --- |
| 业务、权限、计分、题目版本 | 自研模型、接口、测试和审计 | 参考行为，不直接复制整套系统 |
| 判题调度与节点管理 | 自研任务协议和恢复逻辑 | 参考成熟 OJ 的设计 |
| 受限执行 | 定义调用契约、权限和资源限制 | 评估 go-judge 等沙箱；选择前做 Linux 环境验证 |
| 数据生成与检查 | 保存版本、种子、独立验证与审核 | SPJ 优先验证 testlib，其余生成/输入校验复用另行评估；不能替代人工算法审核 |
| 滚榜与查重 | 管理数据版本、权限与人工裁定 | 评估 ICPC Resolver、检测工具，先验证格式兼容性 |

参考源码时核对许可证与归属；借鉴行为设计和复制代码是不同操作，记录实际采用的来源及版本。

## Go 与判题性能的判断

反馈时间由排队、编译、准备沙箱、运行测试、检查答案和结果处理共同组成。Go 服务管理独立的选手程序进程，不能由后端语言推导选手 C++ 程序会改用 Go 执行。

调度开销、GC 与共享资源竞争仍需测量。约 300 人不等于 300 个并行判题任务。没有本项目基准测试，不能给出 Go/C++/Rust 性能比例或容量保证。性能瓶颈出现后以 profile 和可复现实验决定优化范围。

## 备选与代价

- Hydro 二次开发：训练与插件能力可复用，但用户选择掌握业务系统；保留为参考，非当前主线。
- DOMjudge 二次开发：校赛运营成熟，但日常训练和协会业务仍需大量扩展；保留为参考。
- 全部使用 C++ 或 Rust：本轮未选；用户对 Rust 不熟悉，审查与维护成本需要计入。不得让 AI 擅自更换已确认语言。
- Go 自研的代价：鉴权、队伍一致性、封榜、重判、恢复和部署流程都由本项目负责，不能将上游项目的成熟度转移为本项目的质量证明。
