# 运维、离线交付与验证分期

日期：2026-10-25。版本：0.2。状态：工程骨架已建立，运维组件尚未部署、压测或恢复演练。审计后的引入时机见 [开发与交付计划](../phase-1-development-plan.md)。关联 [总体架构](system-design.md)、[存储](storage-design.md)、[CI/CD](../ci-cd.md)。

## 1. 入口与校内依赖

### 当前单机试用资源约束

用户于2026-11-04明确报告服务器为4核、4GB内存、3Mbps公网带宽，并选择控制面、PostgreSQL、Redis与判题Worker全部同机。这是当前部署选择；实际可用内存、系统/CPU架构、磁盘和Docker/沙箱权限尚未在目标机核验，未部署或完成容量验收。API与Worker保持独立进程及鉴权/隔离边界，数据库和Redis保持私有入口。

目标机先执行[只读盘点](../../README.md#试用服务器只读盘点)。采集 JSON 区分当前命名空间的 CPU 亲和性、系统内存与可见 cgroup 各级限额，以及材料、临时文件、数据库卷的可用空间和只读标志。不可见或无法解析的值不能当成无限额；登录进程的限额不一定是最终 Worker 的限额，卷可写标志也不能证明账号有写权限。另行核对目标机 Docker、执行器、权限和隔离能力，再开始受控单槽试验。

首个容量实验从单API、单Worker/单判题槽开始。共同测量系统、数据库、Redis、API、材料快照/文件缓存、编译执行及并发登录Argon2的峰值；根据可用内存与控制面响应确定最终资源及并发上限，不根据4核直接开启四个槽。验证队列等待/积压准入、接收与拒绝语义、OOM/进程退出后的停止与恢复，保留[计划](../phase-1-development-plan.md#p0-范围与环境)中100人在线目标及其混合负载验收缺口。

3Mbps的十进制理论上界为375000B/s，实际吞吐受网络和协议影响，只用于预算换算。题目材料、编译输入及判题结果优先通过同机本地存储/内部通道传递；公网页面冷启动、静态缓存、附件和选手提交另行测量，避免每次判题经公网重复搬运完整大材料。

本机Darwin/LinuxKit arm64的固定镜像、内核及参考验证profile不作为服务器准入证据；目标环境变化后重新验证编译器、执行器隔离、文件/进程/内存边界和停止确认。4GB也不是任意选手可独占的判题额度，Worker缓存与临时文件不能挤占数据库和控制面的存活预算。备份仍须满足下节的恢复目标与独立故障域要求，具体介质待落实。

优先验证 Nginx 开源版、同源静态页面/API、校内可信 HTTPS 与 chrony。入口分流算法和参数以实测定版，不把商业版本能力当作开源版能力。

- 校内 DNS、证书链与时间服务须在外网断开后可用。条件允许时使用受信任的域名证书，否则提前分发校内 CA 信任，不能用忽略浏览器证书警告作为验收。
- 静态文件、编辑器、字体、图片、公式和工具链在本地完整提供。哈希静态资源可缓存，HTML 保持可更新，私有 API 不进共享公开缓存；历史草稿和迟到请求不能串账号。
- 数据库、Redis、监控及沙箱管理端口不开放给选手；只信任明确配置的代理转发头。Worker mTLS 独立于用户入口；同机 Unix socket 是可验证方案，跨主机使用受控加密连接。
- 服务端时钟是接收时间依据，浏览器倒计时仅展示；监测偏差并受控校时，不在比赛中随意跳变。DNS、证书、时间拓扑和运维权限仍待现场确认。
- 用新设备/无缓存浏览器在断外网后验证冷启动、登录、服务重启、提交、榜单和赛务，不能只验证已有连接页面。

本地[冷 HTTPS 浏览器专项](../../README.md#浏览器账号专项)区分未知 CA 拒绝和临时配置受信后的页面加载与真实登录。它限制浏览器使用回环夹具，覆盖桌面和窄屏的本地资源；校内 DNS、证书分发、时间服务及整机断网仍需现场证据。

## 2. 可观测性

结构化日志从骨架引入；训练试用须有健康、队列积压和系统错误可见性。Prometheus、Grafana OSS 与 Alertmanager 按实际监控/值守目标分阶段引入，不作为首条判题路径的前置；正式比赛前落实校内可用的监控告警并演练。精确版本、资源消耗与部署方式待验证，不预设集中式日志集群或全链路追踪平台。

- 指标覆盖接收成功/拒绝/错误及延迟、分级队列最老等待/吞吐、Worker 心跳/槽位/阶段耗时/SE/租约恢复、数据库锁与连接、Redis、存储水位、投影延迟和后台失败。
- 请求、提交、任务、尝试、节点和比赛 ID 用于日志关联；不能把高基数业务 ID 无界放入指标标签。普通日志不记源码、测试数据、令牌或私钥；完整诊断按权限留存。
- 告警分级、分组去重，包含处理入口，支持维护静默和恢复通知；校内断外网时基础看板及告警可用，具体通知渠道依现场条件确定。
- 普通遥测故障不阻断判题；必须留痕的业务审计与业务变更可靠持久化，不能因“监控可降级”绕过强制审计。
- 采集频率、阈值、日志/审计保留和容量预算待硬件及运维条件明确，不填写未经验证的可用性指标。

### 判题运维快照

值守人员可通过 [judge-snapshot 维护命令](../../README.md#判题运维快照) 读取一次聚合快照。当前排队和运行不受时间窗口限制；最老排队时间是该提交的原接收时间，重判或重新排队不会重置它。运行中租约须匹配当前判题及恢复代次、尝试号、启用节点、节点凭证版本和有效期。

同一快照按节点去重汇总当前有效租约，输出 `nodes_with_current_lease` 和 `enabled_nodes_without_current_lease`，不输出节点标识。无有效租约的启用节点可能只是空闲；有效租约在断连后也可能尚未过期。这两个计数不能替代 Worker 心跳、可达性或实测容量；启用槽位数仍是配置值。

近期统计以数据库观察时点及显式的 1–60 分钟接收窗口为准。每笔提交只计一次；当前判题和恢复代次有已上报 SE 的任务计入系统错误，即使重试后完成也保留该观察。已耗尽恢复次数的任务另计，两项可重叠；此窗口按接收时间划分，不等同于最近 N 分钟的事件流。

聚合使用单条查询和只读事务，不申请判题行锁，不返回节点名、账号、源码、尝试令牌或结果原文。没有新增索引；近期统计仍可能扫历史接收记录，只供人工诊断，不作健康探针或高频采集。连接或查询超时不返回部分数据。采样不会改变判题状态，但仍消耗数据库资源。

Docker Desktop arm64 的 PostgreSQL 14 隔离验证使用 50,001 笔合成提交、49,901 条尝试和 102 笔未终止任务。15 分钟窗口的自然 `EXPLAIN (ANALYZE, BUFFERS)` 用现有部分索引读取活动队列，并在近期统计中扫描历史提交；该次执行约 12.5 毫秒。该样本不代表生产数据分布、缓存或并发采集开销。

### 会话 API 就绪检查

普通会话 API 在现有 TLS 监听器上提供 `GET /api/v1/readyz`。在同一秒级预算内核对数据库 schema、会话恢复开关和 Redis PING；成功或故障的观察最多复用一秒，并合并并发请求，不启动后台轮询。不使用 Cookie、续期或改写依赖；输出只含总体状态。排空开始后即不再报告就绪，并等待在途检查结束再关闭客户端。

`/api/v1/healthz` 保持进程存活含义；默认 bootstrap 或实验入口不提供会话就绪。探针不代表 Worker、判题材料、邮件投递或校内网络就绪。值守网络路径沿用 TLS／mTLS 边界，不为探针新开管理端口；现场 Redis ACL 若按命令限制，须允许该运行时角色使用 PING。

## 3. 一致性备份与恢复

采用一致性恢复集合、独立存储副本和定期真实恢复演练。M1 目标为 RPO ≤ 24 小时、RTO ≤ 4 小时；独立介质和责任人仍须落地。小规模试用可使用逻辑备份＋不可变材料清单，数据库 pgBackRest、文件 restic 保留为后续验证路线。逻辑备份不承诺 PITR，真实用户写入前必须完成所选方案的恢复验证。

- 集合包括所选数据库备份（采用物理备份/PITR 时含所需 WAL）、匹配的材料清单与全部引用文件、必要配置、发布/工具链版本及受保护密钥。密钥备份独立管理；Redis 活动会话、Worker 缓存和临时文件可重建，本地浏览器草稿不属于服务端备份。
- 数据库时间点恢复必须匹配完整材料与密钥，不能仅凭连续 WAL 承诺任意业务时间点都可恢复。发布、清理和备份共同保护可恢复引用。
- 至少一份副本位于独立设备/主机故障域，同机另一目录或 Worker 缓存不算独立备份；具体介质与离线搬运条件待确认。
- 恢复建立新恢复代次，拒绝旧节点租约和迟到结果，核验后重新入队。默认撤销旧会话及短期邮件令牌；启用发信前核对恢复后的待发业务，避免旧任务重新发出有效敏感链接。
- 隔离环境验证账号登录、历史源码和材料读取、实际判题、重测、榜单及权限；保存恢复时间、丢失范围、哈希检查与限制。频率、保留、容量和演练周期按现场条件确定。
- 周期备份不能证明已接收提交在灾难中零损失；需要更高连续性时另验冗余与故障切换。版本准入包含最新安全公告及密钥历史风险，不把升级软件等同于旧密钥已安全。

还原后、解除隔离前先做[恢复材料核验](storage-design.md#恢复材料核验)。数据库引用与文件不匹配时，不继续开放 API 或 Worker。

逻辑备份可用[捕获命令](storage-design.md#捕获逻辑备份)生成同一数据库快照对应的归档和材料集合。先保护不可变源文件，再独立保存完成清单摘要；转移到独立介质后、启动还原前，按[接收核验](storage-design.md#核验收到的逻辑备份)检查收到的全部文件。捕获或接收核验成功都不代表异机恢复验收。

### 试用恢复计时与证据

演练前登记源主机、独立副本位置、恢复目标与责任人。RPO 从 `manifest.json` 的数据库快照时间算到宣布故障的时刻；只有在该时刻前已离开源故障域且核验过的副本计入。RTO 从宣布故障算到所有必要观测完成，包含材料校验、服务恢复、旧凭据拒绝及历史提交重判。用同一可信 UTC 时间基准记录，证明源主机已隔离并保持隔离。原始凭据、真实源码和密钥不写入验收记录。

记录文件 `format` 为 `oj.m1-restore-evidence.v1`，包括 `source_domain`、`backup_domain`、`restore_domain`（使用稳定的实际故障域标识）、独立渠道保存的 `manifest_sha256`、`offsite_verified_at`、`fault_declared_at`，以及 `checks`。`checks` 必须包含 `source_isolated`、`materials_verified`、`old_credentials_rejected`、`service_restored` 和 `historical_submission_rejudged`；每项填写 `passed`（布尔）、`at`（UTC ISO 时间）和 `evidence_sha256`（独立留存的脱敏记录摘要）。`old_credentials_rejected` 按部署能力覆盖旧 Cookie、邮件令牌及 Worker 租约；`historical_submission_rejudged` 核对历史提交标识、原结果保留及新判题结果，不用新提交替代。

每项脱敏观测单独保存为 `<观测项>.txt`（例如 `source_isolated.txt`），每份非空且最多 1 MiB，计算原始字节的 SHA-256 后填入对应条目。同一份记录不得复制给多个检查项。确认旧凭据被拒绝后才能将恢复服务交还用户；可先在仍隔离的服务上验证。观察文件和汇总记录在核对时保持静止。

在原始快照与观测记录均可回读后，运行 [计时核对命令](../../README.md#核对-m1-恢复证据)。它验证清单与五份观察文件的摘要、时序和数值门槛，输出是否具备人工复核条件。负责人仍须核对证据来源和内容、实际故障域、源主机隔离及复判结果后再确认验收。同机试跑只作预演。

### 恢复提交租约

先停止旧控制端与 Worker，隔离恢复副本，禁止 API、控制端和 Worker 连接。核对实际主机、端口、数据库、恢复点及材料清单后，运行 [README 中的维护命令](../../README.md#http-到真实判题终态专项)。独立连接变量及数据库名确认可减少误连；同名库和无锁冲突都不能证明隔离，不能在在线库上执行。

单事务在提交任务表和尝试表取得不等待的独占锁。任一运行任务缺少同判题代次、恢复代次和尝试号的租约时拒绝；否则将备份里的所有 `leased` 尝试标为 `expired`，包括还占用节点额度的旧代次尝试，并将 `running` 任务重新排队。恢复代次加一，判题代次、队列顺序、源码和历史记录保持；重新认领从尝试 1 开始，该新代次仍最多三次。已经排队或终态的任务不改；已完成结果的完全相同回执仍可只读确认。旧在途租约不能续租、读取材料或提交结果。

命令输出作废租约和重新排队数量，事务预算 20 秒，在锁内检查和修改在途记录。锁冲突、校验或执行失败须保持隔离并排查，不能直接开放。若提交结果未知，在尚未开放的同一副本上可重跑；一次成功后重跑应为 `0/0`。无需 schema 迁移；不能通过倒退恢复代次来回滚，否则可能重新授权旧结果。此操作不轮换 Worker 节点凭据，不处理参考验证任务、会话或邮件令牌，也不负责整体重新开放。

### 恢复普通会话

1. 用外部维护窗口独占恢复副本；停止并隔离旧 API 和 Redis 端点，禁止其他实例访问恢复库和新 Redis。核对实际主机、端口、库名、恢复点和配置，确认不是在线库。库名一致不能证明端点正确。
2. 通过[维护命令](../../README.md#会话恢复维护)查看状态并换代关闭。使用 `OJ_RESTORED_SESSION_CONFIG_FILE`，凭据仍遵循会话配置的固定环境名；`status` 和 `close` 不读取监听证书、Redis 凭据、登录秘密或密码名单。保留 `close` 回执中的代次；重复 `close` 会换代，未知回执先查状态。
3. 从独立可信来源核对备份之后的密码变更、封禁、邮箱状态和角色，使用获授权的维护渠道补回事实并留痕。无法确认的账号继续隔离，不能仅凭回档库推断已对账。`--accounts-reviewed` 是运维人员确认，不是命令自动审计账号。
4. 让恢复配置指向新的专用 Redis 7.2 主实例，在隔离下以本轮代次和显式确认开放。命令检查 DB 0 为空、运行配置满足会话协议，按现行密钥与策略初始化登录限流，以及显式配置的改密和邮箱限流，再用 PostgreSQL 条件更新开放。配置 `email_limits` 本身不启用公开路由。空库检查只证明检查时为空；Redis 的专用性及过程独占由外部维护窗口保证。
5. 任一步失败先保持隔离并查看状态。Redis 初始化或 PostgreSQL 回执可能只完成一部分；命令不删除数据、不自动重试或补偿。状态仍关闭且 Redis 已变更或变更未知时，改用另一空实例；状态已开放时先核对本轮代次、配置和登录实测，再决定是否重新对外开放，不能盲目换代。以新配置启动 API，核对旧 Cookie 被拒、已知封禁仍生效、允许的账号能登录；随后按发布流程解除隔离。

命令协调普通会话及其限流空间；换代也会使旧邮件令牌和依赖旧作者授权的参考验证申请失效。命令不清除旧任务，也不自动做账号对账、停机、网络隔离或启动 API。无 schema 迁移；不得通过旧库或旧代次回滚已确认的撤销。

### 回档后的旧邮件授权

从还原前到换代关闭、账号对账及重新开放完成，须保持恢复库与 API、发信执行器隔离。只还原数据库会同时还原备份内的旧摘要和待发密文；即使原库后来已经消费链接，也不能直接开放恢复库。真实归档回归在独立的本地 PostgreSQL 实例还原同一份备份，验证旧激活与找回载荷原先能重新准备，换代关闭时及以新代次开放后均无法准备或消费。拒绝时旧密文仍在发送窗口内，账号状态未改变；新代次仍可签发和消费。

同一回归还原真实 River 队列，使用发送器的领取与投递资格检查。恢复后的两条旧任务在请求共享发送许可和调用 SMTP 前即被判为失效；确认终态时删除短期密文，保留令牌摘要。新任务可取得真实数据库许可并到达测试 SMTP 边界，有效令牌仍可消费。回归使用 SMTP 替身及同一宿主上的两套 PostgreSQL，未启动独立邮件进程，也未验证独立故障域、RPO 或 RTO。

重新开放邮件前还须核对发信配置，并保留独立的累计加密用量账本或换用从未使用过的密钥；不能用回档账本继续复用原密钥额度。

### 回档后的旧参考验证授权

只还原归档会同时还原旧作者授权与旧 Worker 预留。保持参考 Worker 与恢复副本隔离，完成上述换代后才允许连接；按独立可信记录核对 Worker 节点是否仍应启用及其凭据版本，换代本身不撤销节点凭据。

换代关闭时和重新开放后，旧申请的预留即使还未到期，也不能再授权材料读取、续租或首次回报；到期后原申请也不能显式重领。回归使用真实 PostgreSQL 归档证明这些拒绝，并读回申请仍排队、预留没有续期、没有新增报告。此处验证的是数据库授权，不证明旧宿主进程已停止。

换代不清理旧预留、不释放旧申请的队列额度，也不自动重跑；预留行按原期限自然到期。在恢复副本核对阶段，仍获授权的原作者可用新会话按原请求键查回执并取消，释放队列额度。重复取消或提交原创建键只返回取消回执；如需重新验证，须显式使用新键提交，绑定本轮授权。这个流程不会停止已运行的进程，也不等待旧预留到期才释放排队额度。

账号封禁、作者权限撤销或无法找回原键时，旧申请可能仍占额度。真实恢复回归中，补回封禁的作者无法登录，另一作者不能代为取消，其记录仍排队。无法由本人处理的申请，在恢复门禁开放前按下节逐笔核对；不通过重新授予权限、删除记录或反复领取旧任务腾额度。

### 恢复参考验证积压

在普通会话换代关闭之后、重新开放之前，保持 API 和 Worker 与恢复副本隔离，确认主机、库名、恢复点和本轮关闭代次。使用 [README 的维护命令](../../README.md#会话恢复维护)。`list` 按申请 ID 每页最多列出 20 笔旧代次排队申请，可带上页 `next_after` 继续；分页不是跨页快照。`status` 按旧申请 ID 查状态，包含申请、草稿、来源、作者标识及时间，不输出请求键、预留令牌或证据内容。核对确实无法由本人处理的申请后，才逐笔执行带 `--confirm-cancel` 的 `cancel`，留存核对依据及回执。

维护事务核对连接库名并锁定精确关闭代次；取消再按队列策略、申请顺序取锁。门禁开放、代次不符、当前代次申请或已接纳报告都不会被取消。仅将选定的旧 queued 申请转为 `cancelled`，释放一个排队额度；原授权、计划、领取历史、预留、报告及其他申请保持。预留按原期限到期，取消不证明旧进程停止。没有批量取消、后台扫描、Redis 操作或自动重开。

回执不确定时，在同一关闭代次按原 ID 查 `status`；已取消的申请重试返回原取消时间。若代次或隔离状态变化，先停下来核对现场。无需迁移或新增索引；可停用命令或回退二进制，已提交的取消不逆转，恢复后需要执行的验证应由当前有权限的作者用新键重新申请。

## 4. 保留与回收

采用分类保留、引用保护、两阶段回收和空间水位。历史版本可归档隐藏，归档不等于物理删除。

- 正式提交、有效/历史结果与必要审计不能因磁盘压力自动删除；期限未定前不启用核心记录自动销毁。题目材料、原包来源、历史提交、重测、在途任务及备份恢复链共同决定保护范围。
- 自测、暂存与诊断有界临时保留；需要长期留证的材料显式转存。原始题包只读保留，退出保留须经过授权规则，不因重新导入覆盖。
- 回收先生成候选、等待宽限，再重新检查引用及并发发布/任务保护后删除；过程可预览、审计、中断恢复，低峰执行。单次无锁引用快照不足以安全删除。
- Worker 缓存按容量和近期使用清理，不删除正在使用的材料；租约过期不证明旧进程已停止，须结合取消、硬时限和本地占用保护。
- 水位先清可重建/已过期内容，再暂停后台工作，必要时拒绝新上传/任务；保留已接收提交。备份快照、WAL、大文件与密钥的清理必须协调；浏览器草稿继续无按时间自动删除。

## 5. 发布与回滚

采用不可变制品、完整离线交付包、短维护窗口和受控回滚；Linux Docker Engine＋Compose 为优先验证部署路线，未确认现场权限，不依赖付费桌面组件。

- 构建一次，测试到生产晋级同一提交/版本/digest 制品。离线包包含应用、前端资源、语言与检查器环境、迁移、模板、校验清单、安装及恢复说明；明确操作系统和容器运行时前置条件，不运行时联网下载。
- 发布前检查权限、验收、备份及模式兼容；停止新写入和任务认领，按有界排空策略处理在途任务，独立执行 Goose 显式锁迁移，再切换、冒烟和观察。未排空任务按既定租约协议受控恢复，不直接丢弃。
- 应用回滚须与现有数据库兼容；不可逆模式变更优先向前修复，不用恢复旧数据库覆盖发布后新提交来冒充普通回滚。
- 正式比赛冻结常规发布，紧急修复记录授权、最小验证、影响和恢复路径。前端升级不强迫刷新丢草稿，API 保留兼容窗口。
- 校内/外部部署仅一个比赛权威写入端，切换受控，不引入自动双主。凭据不放公开包，部署审计记录版本和结果。窗口、排空时限及拓扑待验证，不承诺零停机。

[试用应用包 v2](../../README.md#试用离线应用制品)将 Nginx 模板与二进制、静态前端一同封存。隔离冷启动仅从通过摘要核验的包复制模板，不从接收端工作树选择配置。正式域名、证书和按目标拓扑生成的配置仍需单独登记并验收。

### 兼容回退专项

`rollback-loop` 在固定 Desktop 环境用同一个新建 PostgreSQL 和材料目录，顺序运行旧版 `771ff3f`、当前版、同一旧版的实验 API、mTLS 控制端和真实 Worker。旧版先完成一份合成提交；切换前停止接收并排空，独立迁移从 schema 20 升至 25。旧版 API 在 25 拒绝启动。新版完成一份提交，Worker 停止后再接收一份留在队列。

新版进程退出后逐步回退到 20，每一步核对 schema、提交、队列任务和尝试数量。Down25 只移除审核分配列表索引；Down24 和 Down21 分别要求重判审计与邮件令牌账本为空。新版 API 在回到 schema 20 后拒绝启动。旧版按原键读回两个终态及排队回执，并处理已经接收的排队任务。专项验证三份原始源码、两个已有报告和三次完成尝试；回退不换库、不恢复旧备份。

本地专项覆盖指定版本对、固定材料及受保护账本为空时的有序跨 schema 切换。非空重判与邮件账本由各自回退门禁保护；不适用于仍在执行的任务、现场拓扑、正式离线发布包或比赛现场切换。

### 实验判题离线包

[专用 Ubuntu 实验](../../README.md#专用-ubuntu-vm-判题实验)封存 API、控制端、Worker、迁移工具、测试驱动和两份固定的无标签镜像。独立取得的清单摘要绑定文件及声明的源码版本；接收端核对精确路径、权限、大小和摘要，并检查镜像归档的固定 OCI 描述、Linux arm64 运行层和 Docker 导入条目。核验不解包镜像或连接 Docker。受控 VM 脚本核验成功后才导入，回读镜像 ID，再禁止拉取并执行真实合成判题。

摘要由可信构建方单独提供，不能替代签名或证明制品确实由所声明提交构建。接收目录由 root 控制，在核验、导入和运行之间保持静止。空库复验在专用 VM 内使用全新 Docker 和 containerd 数据目录、独立挂载和网络空间。导入前确认 containerd 无镜像内容、Docker 无镜像；导入后验证完整镜像 ID 集合，禁拉取判题通过。空库开关只检查 Docker 镜像列表，不能单独证明底层没有缓存；不要从现有库删镜像来取得证据。

VM 已安装 Docker Engine。该专项不证明从空白操作系统安装 Docker、整个 VM 断网、完整应用离线包、冷浏览器、校内 DNS／HTTPS／时间或现场发布可用。

## 6. 测试路线与实施阶段

采用 Go 标准 testing 验证核心规则；真实 PostgreSQL/Redis 集成优先验证 Testcontainers for Go；前端采用 Vitest＋React Testing Library，端到端采用 Playwright。骨架已建立 Go 与 Vitest 测试及实际构建命令，见 README；React Testing Library、数据库集成与端到端自动化尚未接入，真实远端 CI 尚未运行。后续组件版本与资源条件实施时准入。

- 依需求验证成功、边界、失败和恢复，不以覆盖率或照抄实现代替行为测试。固定回归题集覆盖正确/错误/超时/畸形输出、检查器故障、多语言和环境版本。
- 专用可信 Linux 节点验证沙箱、故障、混合负载、断外网和恢复；快速 CI 与重型演练分开，不向不可信 PR 分配生产凭据或高权限执行环境。
- 至少两个 API/Worker 验证跨实例会话、幂等、领取、撤销、重测与事件重放；同机实例不证明主机容灾。容量和恢复数值在硬件明确后定标。

| 阶段 | 已确认范围与通过条件 |
| --- | --- |
| 0A：工程骨架 | API 健康接口、前端真实连接、Worker 诚实标识及构建/测试；不代表真实判题 |
| 0B：关键技术验证 | 验证数据库任务、会话、Linux 沙箱、GNU++17 文本题及节点认证；保存可复现结果，实验不算产品交付 |
| 1A：训练试用 | 登录、已审核授权题目、单文件提交与草稿、真实判题/查询、关键权限与恢复；语言与题型按实际试用需要冻结 |
| 1B：完整训练 | 补齐全部首批语言、文本/浮点/SPJ 与日常账号流程；多文件/ZIP、自测另排训练增强，具体边界见交付基线 |
| 2：战队训练 | 长期战队、邀请、版本化题单/任务、训练赛、补题及历史访问 |
| 3：正式比赛 | 报名与账号、ICPC 计分、封榜、答疑、气球、查重、审核重测与滚榜；完成校内离线、故障及目标混合负载演练 |

分期安排不取消已确认的整体需求，不把所有阶段都说成第一个训练交付。每阶段均包含对应测试、运维交付、文档和知识沉淀。

首个技术闭环用 GNU++17 文本题：固定题目/材料/源码与语言配置 → 提交和任务同事务保存并返回 ID → 经认证 Worker 认领、编译/运行/检查 → 有效租约/代次回报并在前端查询。必须同时验证重复请求、回执不明、节点失联、迟到回报及材料不可读。随后补齐其他语言、浮点和 SPJ，单一 C++ 示例不代表阶段 1 完成。组件准入失败时在同一业务契约下评估备选，日期等硬件和条件明确后确定。
