# 持久化参考验证申请

本页描述 PostgreSQL 申请账本、作者申请入口和内部预期计划。专用参考 Worker 可通过默认关闭的节点接口领取短预留，在有效期内下载与计划绑定的材料；另行启用后可在单宿主隔离环境续期、执行并提交确定结果。作者入口管理本人申请，草稿 `not-run`、生产配置及发布阻断保持。

## 作者申请入口

普通 HTTPS 会话配置显式设置 `private_drafts.reference_requests: true` 后，[参考申请 API](../api/problem-reference-requests.openapi.yaml)允许本人创建、按原键查询和取消。仍须独立配置排队额度。沿用私有草稿的固定 Host、可选受信 mTLS 代理和同源 POST 门禁；`X-OJ-Expected-Subject` 与实际 Cookie 会话不一致时，在访问账本前返回 409。当前角色、恢复与账号状态在 PostgreSQL 事务中检查，读取和取消仅限本人；其他作者或不存在的申请同为 404。HTTP 不从客户端接收来源、材料、Profile、Plan 或判定。

预览页在严格 IndexedDB 事务提交后才发送，按账号与草稿保留当前请求键。刷新、账号变化或恢复页面只清除显示，不自动查询或提交。丢失确认后显式查原键；404 仅代表本次未观察到，可用同键重试。确认终态后才可为同一草稿新建请求；没有跨设备申请发现，清除浏览器数据会丢失本机键。取消仅更新账本，不承诺立即停止在途 Worker。回执只有 ID、原键、草稿 ID、状态和创建/取消时间；`reported` 表示收到可信报告，不代表通过或发布。

确认申请仍待完成后，作者可按原键显式 POST `/prepare` 并 GET `/plan`。202 仅表示本进程受理（`ready:false`）；GET 只返回持久正式计划是否已记录。两条路由都不返回计划、摘要、材料或凭据。固定卷积题的新计划同时核验对拍材料。刷新不会启动准备；未知结果或重启后用原键查状态，需要时再显式提交。

确认原回执为 `reported` 后，可在草稿预览点击“查看验证结果”，或按原键 GET `/report`。接口重新核对普通会话、当前作者角色及草稿归属和内容身份；排队、取消、缺失或不属于本人的申请均无结果。最多 2048 字节，包含草稿内容版本、正式判定和通过/总点数，以及可选的对拍一致数和首个生成差异（小输入与两组系数）。旧正式报告、以及尚未进入对拍的正式失败报告，对拍字段为 `null`。历史回读核对原计划和证据，不要求原 Worker 仍可用；不返回正式输入、答案、逐点明细或 Worker 资料。结果只显示在当前页面内存中，不写入本地申请日志。

准备不在 HTTP 请求内读取大材料。每个启用 API 进程最多一个活动任务，无等待队列，其他申请忙时返回 429。活动任务最多三分钟，只在内存持有同一会话凭据，冻结前后重验；HTTP 断开不撤销已受理任务。取消或撤权先于最终事务时不得写入计划，但不承诺立即中断跨实例材料 I/O。关闭运行时先排空 HTTP，再取消和排空准备任务，最后关闭材料和存储连接；没有持久委托、启动扫描或自动重跑。关闭配置并重启保留原账本。

## 身份与可信配置

`NewCatalog`只接收维护装配层已通过`problem.LoadBundle`及显式受信来源锁验证的Prepared，保存脱离底层文件的ImportIdentity及由`problemvalidation.ResolveSource`产生的完整Profile。最多十来源且共用同一来源锁；允许空目录，以便退役全部来源后仍读取/取消既有申请。配置目录不持有Prepared或大材料文件，创建后修改输入map、关闭Prepared或移动材料目录不改变已保存的配置。

每份配置固定`source_id`、题目内容version、覆盖全部引用的import_revision、source_lock_sha256、`oj.reference-request.v1`及最多16KiB紧凑Profile原始JSON和SHA-256。Profile从封闭Resolver生成，调用者不能为某个申请指定预算。配置副本深复制字节，读取历史回执验证原字节摘要，不用当前Resolver重写旧Profile。`Specification.Valid`仅验证历史身份结构和字节一致性，不是Profile语义、材料或执行准入检查。允许受信合成锁验证持久化协议，不代表它可以通过实际Runner的固定来源锁门禁；现有Profile仅在固定Desktop维护环境验过，不能套用于未知服务器。

`Service.Enqueue(ctx, credential, requestKey, draftID)`只接受普通会话凭据、owner范围请求键及草稿ID；Receipt/Cancel只接凭据和原键。每次通过实际SessionReader取得当前ProblemActor，再由存储在同一READ COMMITTED事务重新核验恢复、账号和当前作者角色。凭据不入库；客户端不能提交主体、权限修订、来源锁、Plan/Profile或执行报告。单token退出在最后会话观察之后仍遵循已接受在途边界，不承诺Redis与PG原子撤回。

入库保存原`ProblemAuthorSnapshot`中的AuthGeneration、RecoveryID、RoleRevision及owner。以后受权准备、领取或接纳报告必须重新检查并比较完整快照；当前enabled不能使撤权后重授的旧任务复活。当前作者可读回/取消本人旧申请，回执和取消不把旧快照改成新权限。

## 事务、幂等与取消

锁序为恢复→账号→角色→本人草稿→policy→申请。problem公开窄`ReferenceAccess`适配器在调用方同一事务检查权限并锁定草稿身份；申请模块不引用problem或identity私有SQL。调用使用五秒context预算，另有独立一秒尽力回滚；不保证远端事务已结束。材料I/O及程序执行不在事务内。

申请先以owner/key无行锁查询原回执：相同draft_id返回原记录及原配置，不同draft_id为冲突。新申请才锁定本人草稿，再锁policy；取得policy后必须重新查询原键，最后才匹配当前目录与检查额度。第二次查询处理“并发赢家刚占满最后额度”的情况，不能将同键恢复误报为额度不足。原键恢复不依赖当前目录、额度或policy仍可用，也不会创建新记录。其他owner的键和不存在的键同为not-found。

申请从 `queued` 进入 `cancelled` 或 `reported` 终态。取消先按 owner/key 只读定位，再锁草稿、policy 和申请行，仅在仍为 queued 时更新；重复取消返回原终态和已有取消时间。它保留原 ID、配置、授权快照及历史，不停止 Worker，也不会重新排队。

新申请或取消在COMMIT回执失去且结果不确定时返回零结果及`ErrCommitUnknown`；保留原键，通过独立只读Receipt恢复。上下文在存储已成功后取消也按写回执未知处理。not-found仅是当次观察，不能证明另一个请求不在途；不使用新键绕过未知结果。只读回执失败不触发重写或清理。

## 有界排队与未完成边界

schema9 默认创建空 policy，缺失时拒绝新申请。受信维护者用 README 的 `migrate reference-backlog` 命令显式设置；启动不会自动写入。`1≤Owner≤Global≤1024`，具体值是维护选择，不是硬件容量结论。下调额度不删除已接受记录；旧原键仍可恢复，新的不同键在超额时拒绝。

新增、取消和首报接纳都串行取得 singleton policy 行锁。计数沿用积压准入的 MATERIALIZED 窗口，最多读取 Global 条 queued：达到窗口立即拒绝，未满时全局与本人计数均精确。部分 B-tree `problem_reference_requests_queued_owner(owner_subject_id,id) WHERE state='queued'` 排除终态历史，支持有界计数；入队和离队产生索引与 WAL 写入，实际代价依分布而定。owner/key 唯一索引支持回执，主键支持固定 ID，配套真实查询计划归交付记录。

额度只限制 queued 数量，不限制历史增长、请求频率或正在执行的沙箱数量。永久撤权、账号禁用会留下仍占额度的 queued；本期没有隐式清理或绕过权限的维护取消。判题、维护参考验证与参考领取命令默认使用[同机共享执行槽](architecture/api-worker-design.md#同机共享执行槽)；后续参考执行须继续持有该门禁。两个独立队列限额不提供共享执行容量。

申请阶段不读大材料，不填Plan摘要、attempt、判定或Stop证明。内部 `Request.BindDraft` 可将回读的草稿元数据与 queued 回执绑定：核对草稿 ID、owner、私有状态、来源、版本和来源锁，按导入时的字节顺序对逻辑引用排序，并用原始文档字节和完整引用重新计算导入修订。版本相同但缺失、替换或新增证据引用也会拒绝。成功结果是独立副本；此操作不读数据库或对象存储，也不能用旧回执替代当前授权或当前申请状态。

## 从持久化对象冻结参考计划

内部 `Request.FreezeDraft` 使用已授权回读的草稿和申请。它先核对 queued 回执、完整导入修订，并要求原 Profile JSON 与当前受支持的完整 Profile 逐字相同；退役或变更的配置仍可读回执，但不可用新配置继续准备。调用方应在授权事务结束后用有期限的 context 调用，保存或执行计划前须重验实时申请状态及原授权快照。此方法不接管事务、租约或运行准入。

材料按 SHA-256 和长度从私有对象存储打开，不使用草稿的 bundle 路径。沿用固定来源布局和大小上限：校验完整的点目录与哈希清单，再依序冻结参考源码、允许的编译依赖及所有输入和答案。逐对象关闭存储快照，在 `MaxInFlight=1` 时也能工作。冻结文件为匿名临时文件；复制时复核实际长度和摘要，任何缺失、损坏或取消都不会返回部分计划。返回的 Plan 只含标识，摘要与同一导入的原维护路径一致；读取冻结字节不再访问存储或原 bundle。调用方须关闭快照以释放文件和进程内快照槽。

本路径包含一个冻结文件和至多一个正在复制的对象快照，两份临时文件分别使用进程临时目录和对象根。它与既有磁盘维护快照共享进程内单槽；这不是跨进程或判题/参考任务共享的执行槽。没有读取题面、图片、未选中的生成器或来源报告正文；其引用仍受完整导入修订约束。冻结成功不代表检查器域、运行环境、题源执行、报告接纳或发布通过。

## 实时复核与预期计划写入

内部 `PlanService.Prepare` 只接受普通会话凭据和原申请键。首次观察会话后，通过当前授权读取本人申请及草稿；冻结使用调用期限与三分钟准备上限中较短者。成功冻结并关闭快照后再次读取**同一凭据**，要求前后主体、账号授权代次和恢复代次一致。随后开启短 READ COMMITTED 事务，锁住恢复、账号、作者角色、本人草稿及申请行，核对实时授权快照与申请原快照相同（包括角色修订），再确认申请 ID、草稿修订、原 Profile 字节和 `queued` 状态未变化。材料 I/O、会话读取均在最终写入事务外；最后一次会话观察之后的单 token 退出仍遵循已接受在途合同。

预期计划由控制端冻结结果生成，写入原始 Plan JSON 与 SHA-256，长度上限 64 KiB，只有材料标识、顺序与来源身份，没有对象正文、凭据、判定或运行证明。申请行锁与取消串行化：取消先提交则不写计划；计划先提交则后续取消保留历史。计划不改变 queued 额度，因此不获取全局 policy 行锁。同一申请只能写入一行；重复准备仍须重新通过授权与状态检查，同字节幂等，不同字节拒绝且保留原值。

写入 COMMIT 结果不明时保留原键，调用只读 `PlanService.Receipt` 独立恢复。读取复核当前本人作者权、计划字节/摘要和申请身份；不会改写历史 Profile 或重新执行材料冻结。当前 Plan JSON 形状属于历史读取合同，变更字段或编码须保留兼容读取。读取校验不能替代执行准入。取消或重授后可在当前权限下读取既有计划，但不能用历史计划或回执恢复执行资格。

### 卷积独立对拍的预期计划

固定来源锁的 `convolution_mod` 新计划在正式材料关闭后，再按[草稿修订冻结两份解法](reference-validation.md#已入库草稿的卷积对拍材料)。两个阶段共享三分钟期限；任一解法缺失、损坏或超时均不写入正式计划。两份材料校验完成后才重新观察会话并进入同一个授权事务。

正式计划的编码和摘要不变。对拍计划有独立的规范 JSON 和 SHA-256（最多 2 KiB），固定草稿、来源锁和版本、两份解法对象、语料 ID、种子、摘要、点数、Profile 和正式计划摘要。单次 INSERT 写入同一行；原键读取返回实际保存的两个计划。历史正式计划仍可单独读取或重放，不在升级时回填。其他来源沿用正式计划查询。Worker 可通过[专用路由](#有效预留内的卷积对拍材料)获取两份解法，并在同一正式预留内执行和回报。

## 专用 Worker 领取

受信控制端配置 `OJ_WORKER_REFERENCE_NODE_ID` 后，指定且仍启用的节点可使用独立 URI SAN `spiffe://onlinejudge/reference-worker/{node_id}/{credential_version}` 调用[参考领取接口](../api/worker.openapi.yaml)。每次重验证书与节点状态；普通判题证书不能调用参考入口，参考证书也不能调用判题领取、续租、材料或回报。默认不启用。多个控制端使用同一数据库时，共享同一预留记录。

Worker 按申请 ID、固定来源和预期 Plan SHA-256 发起一次请求。先拿[同机宿主锁和对应物理槽锁](architecture/api-worker-design.md#同机共享执行槽)，忙或隔离时不发 HTTP；A+B 固定使用 primary，其余按来源对应固定档，不接双 M0 或槽别名。事务先锁节点，再以只读定位取得申请原作者，按恢复、账号、角色、草稿、申请、Plan 的顺序锁定并复核。只接受仍 queued、原授权代次和角色修订未变、草稿版本/导入修订匹配、当前固定来源锁及 Profile 原字节匹配、Plan 编码及请求摘要一致的申请。

数据库只保留一条全局参考预留，使用数据库时钟，30 秒内拒绝所有重复或其他领取；过期后才可重新复核并替换为新令牌。取消保持原预留期限，不重开执行权限，不更改草稿；丢响应可能已经占用预留，Worker 不自动重试。`claim-reference` 在同一宿主锁内领取并校验材料，结束即关闭匿名快照并释放锁，不启动容器、不打印令牌。仅领取的回执不足以执行或回报。

### 按来源选择已准备申请

控制端在参考执行已启用时，可额外设置 `OJ_WORKER_REFERENCE_DISPATCH=1`。专用 Worker 的 `run-next-reference SOURCE_ID [AFTER_ID]` 根据来源先确定原物理槽，再获取宿主和槽锁，之后才向 `reference/dispatch` 发一次请求。每次按固定来源、C 排序的申请 ID 查询至多八条 queued 候选；对已准备且未记录领取历史的候选走现有授权、计划和预留事务。整个选择最多两秒，最多成功领取一个。空页可能返回 `next_after`，操作者可在下一次显式调用中继续，末页后可从头重查；没有后台自动遍历、FIFO 或跨宿主调度。

首次领取记录与预留同事务写入，目标领取命令也写入（即使只下载材料）。预留过期、被替换、响应丢失或 Worker 未交报告都不会使已领取申请再次参与自动选择。已有计划的迁移历史标为不明，同样排除；需要人工处理时可使用既有显式目标命令，并保留原证据。HTTP 结果不明时当前命令停止，不扫描下一页或开始执行。成功领取后的续期、材料校验、停止和报告沿用原流程。

## 有效预留内的材料下发

控制端同时配置 `OJ_WORKER_REFERENCE_MATERIAL_ROOT` 才启用参考 `assignment` 和 `material` 路由。该路径指向草稿入库使用的、已持久化的私有对象根；不会创建或修复目录，也不读取原 bundle。未配置时领取仍可用，但本版 Worker 的完整领取命令会因材料不可用而失败。材料访问使用同一专用 mTLS 身份，每个请求绑定申请、来源、预期 Plan 摘要和预留令牌；节点及凭据版本必须仍有效。

描述接口返回原 Plan 规范 JSON 的 base64 字节和保守剩余毫秒数，不传作者身份、完整草稿或存储路径。下载只能指定该 Plan 中的源码、固定编译依赖、测试目录/哈希清单或输入/答案的 SHA-256 与大小，不能任意读取对象根。每次操作沿用领取锁序复核原授权、queued 状态、草稿、当前 Profile/来源锁和预期计划，最后锁住唯一预留，再重新查询数据库时钟；等待行锁的时间也消耗预留。下载在事务外完整验证一个对象快照，然后用第二个短事务复核相同权限及计划，才允许写出。两次检查都不修改或延长预留，也不创建 attempt。

数据库剩余时间从事务开始的本地单调时刻换算为更保守的期限，约束对象读取与 HTTP 写出；写出同时设置连接 deadline，慢客户端不能无限占用材料槽。撤权或取消先于最终检查时不发送对象正文；晚于最终检查时可能已有授权字节在途，不保证立即撤回，后续对象会拒绝。传输失败保留截断响应，不追加 JSON。

Worker 从描述请求开始计时，用剩余时间减去完整请求耗时，避免依赖跨机墙钟。它复核操作员固定的摘要、规范编码、内置来源锁及固定布局/依赖/大小预算，再用相同目录解析器独立确认完整有序测试集合。逐对象校验长度和 SHA-256，顺序关闭网络对象，把源码、依赖和所有测试点冻结到共享单槽的匿名磁盘文件；不把整题材料保存在内存。损坏、缺失、截断、超时或最后对象失败都不返回部分快照。快照随调用取消/预留期限失效，须显式关闭释放文件；成功后不再读网络。这验证计划绑定的材料，不重新计算完整草稿导入修订或授予执行资格。

每次描述给出的下载期限不可延长，`claim-reference` 不调用续期。大题在低带宽下可能无法下载完成，失败并清理是预期行为；尤其不能由固定预算上限推断 3Mbps 目标服务器可在期限内完成。材料查询只读取唯一预留行。

### 有效预留内的卷积对拍材料

控制端启用 `OJ_WORKER_REFERENCE_EXECUTION=1` 时，专用 mTLS 节点可用同一个正式预留调用 [`reference/differential/assignment` 和 `reference/differential/material`](../api/worker.openapi.yaml)。前者返回独立计划、摘要和保守剩余时间；后者还必须携带该摘要，只接受两份锁定解法的对象身份。正式材料路由继续使用原来的对象清单。没有独立对拍计划的旧正式申请仍可读正式材料。

两条路由沿用节点、原作者、草稿、申请、计划和预留的锁序。控制端在同一事务读取两份计划，逐对象 I/O 前后复核原授权、预留与计划原值，并对网络写出设置期限。Worker 独立复核正式摘要、规范对拍编码、固定源码角色、语料、Profile、实际字节长度及哈希。两份解法在描述给出的原期限内依序读取，每份最多 64 KiB；任一失败不返回部分材料。描述只在确认预留仍有效且历史计划确实没有对拍记录时返回 204；损坏或失效不允许降级为正式点执行。

## 同机持槽参考执行

控制端须额外设置 `OJ_WORKER_REFERENCE_EXECUTION=1`，且显式配置专用节点与已存在的私有对象根。`run-reference` 使用同一回环 mTLS 地址、固定节点证书和来源档，禁止双槽及槽别名；只启动已经预配、停止且绑定固定所有权/资源的槽。领取、续期、下载、启动、运行、停止和清理期间一直持有原宿主锁与目标槽锁。

首次续期须确认后才下载并执行；续期使用独立连接，每 5 秒发起一次，单次最多 3 秒。本地从发出续期前开始计时，最多使用 25 秒，服务端每次仅将仍有效的同一预留延长至数据库当前时刻加 30 秒。事务复核节点、原授权快照、草稿、申请、固定配置及预期 Plan，取得预留行锁后再次检查期限和完整绑定。没有新表或索引，只有对同一行的期限更新及 WAL；过期、被替换、撤权、取消或回执未知均不自动重试。

已完成的冻结快照绑定这一次监督的上下文；传输仍受原下载期限约束。续期延长的是监督预算，不能复活已取消的快照。执行复核冻结计划摘要与固定来源锁，沿用现有固定预算、全量答案预检及串行逐点验证，不更新草稿或发布状态。

已准备对拍的卷积申请先下载两种材料，再启动同一个固定槽。正式点通过后，朴素解和候选解使用新适配器依序在同一个 Host 内运行；三个阶段共享原宿主传输额度和三分钟执行期限。正式点明确失败时不启动对拍。对拍首个合法差异会结束验证，只有在制品清理和原槽停止都确认时才保留为确定失败证据；租约失效、读写异常或清理失败不提交结果。

丢失授权或取消会先取消工作，再用独立期限停止并确认原容器生命周期，等在途工作退出后才允许清标记；成功同样要求停止确认。启动回执不明但已取得原容器句柄时仍尝试停止；没有可靠句柄或停止期限内不能确认则保留隔离。过期预留可被替换只是数据库账本行为，**不是停止证明**；本阶段依赖同宿主同 UID 的固定槽锁和持久隔离标记，不支持跨 UID、跨宿主调度、代理转发或节点迁移。恢复仍需先确认旧控制操作已排空，再用既有恢复命令核对固定原容器 ID；不得手工清标记。

`run-reference` 只在停止确认、工作排空、材料关闭和槽标记清理均成功后冻结报告。无运行结果、未知续期、基础设施失败、未确认停止和清理失败均不发送。可信报告不产生判题 attempt，也不构成生产验收。

## 参考报告接纳

执行开关开启后，专用 mTLS 节点可提交 `reference/report`，绑定原申请、来源、预期 Plan 摘要和令牌。每个请求体最多 24 KiB；证据是最多 16 KiB 的规范 JSON 字节（外层 base64）。正式证据含原 Profile、总体及逐点结果、用量、固定槽和停止确认；只有合法对拍差异可额外保存固定小规模反例及两端系数，不保存正式材料、解法源码或诊断。停止确认是可信节点的声明，控制端不独立观测容器。

控制端在首报事务复核节点、原授权、草稿、配置及冻结计划，先取 policy 行锁再锁申请；报告只能匹配完整有序点集。AC 需所有点 AC；CE 不运行任何点；WA/RE/TLE/MLE/OLE 需在首个明确失败后保留 `NOT_RUN`。非 CE 编译、AC/WA 点的用量必须符合原固定预算，其他用量仍须非负。基础设施错误 `SE` 不接纳。取得预留锁后，数据库时钟仍须证明原令牌未过期。事务一次保存规范证据和摘要、将申请改为 `reported` 并使该预留失效，释放排队名额。取消不会改变 `reported`；再次验证须新建申请。

已有独立计划的卷积首次正式 AC 必须同时报告对拍通过或合法首差异。控制端用同一锁定计划核对独立摘要、语料、点号、系数长度和模域；差异报告可接纳，但 Worker 返回验证失败。旧正式报告仍可逐字重放。`reported` 仅表示证据已保存，作者可按原键读取摘要；审核和发布门禁另行接入。

[新版十题实测](delivery-log.md#2026-11-11新版题包十题真实报告接纳)从真实 Worker 经专用 mTLS 接纳 254 个正式 AC 和卷积 24 个一致对拍。临时 PostgreSQL 回读核对内容版本、完整导入修订及已消费的预留，草稿均为 `not-run`。

`204` 确认已提交或原结果的完全相同重放。重放仍要求当前专用节点、凭据版本、原作者授权和草稿身份；按保存的令牌摘要、计划摘要与证据原字节比较。原令牌过期或预留已被新申请使用时，可确认历史结果，且不更新新预留或报告。不同绑定或不同证据拒绝。Worker 在同一宿主锁内最多三次发送同一冻结请求，仅未知确认才重放；耗尽后报告未知，不自动重跑。不新增跨进程回放文件或作者报告 HTTP。

### 十题实物报告接纳专项

[手动驱动](../README.md#十题真实报告接纳)在临时 PostgreSQL 及私有材料根中，以合成普通会话逐题执行入库、原键申请与显式计划准备。真实 Darwin Worker 经回环 mTLS 领取、下载、续期、持槽执行并提交报告。夹具用独立数据库连接回读有序正式 AC、停止确认、版本、完整导入修订、证据摘要、已消费预留和终态；下一题须能在全局与作者各一条的队列额度内重新入队。作者服务按原键读到正确摘要，另一已授权作者不能读取。卷积另外要求 24 个独立对拍一致，其他九题不得产生对拍证据。

这是专用 Worker 和 PostgreSQL 实测，不是普通 CI，也不验证 Redis/浏览器会话、部署、完整题目质量或发布。运行失败时保留临时输出，不自动重跑或手清槽标记。

## 迁移与回退

二进制精确要求 schema 14。维护窗口排空并停止旧 API/Worker 及维护写入，独立 `migrate up` 后启动匹配版本；已运行旧进程不会因版本变更自动停止，不滚动混跑。此交付只在隔离临时数据库验证，没有改动持久化 localdev 或目标服务器。

迁移 14 增加可空的对拍计划编码和摘要，不回填。两列必须同时为空或同时合法；查询沿用申请主键，不新增索引或队列查询，仅卷积新计划有额外编码与 WAL 成本。DDL 在维护窗口校验约束。Down14 先锁申请表再锁计划表，只允许没有对拍计划时回退并保留正式计划；已有对拍计划时须前向修复。

迁移 13 增加申请主键的首领历史，回填既有 Plan 的不明历史，并增加只服务按来源选取的 queued 部分索引。每次首次领取增加一条历史及对应索引/WAL；入队和终态更新维护来源索引。旧计数索引继续独立使用。Down13 先锁申请再锁领取历史，历史不为空时拒绝回退；关闭选择开关保留数据，已有证据须前向修复。

迁移 12 增加 `reported` 终态及按申请主键保存的不可变报告。首报写入一份有界证据、更新申请/预留、移出既有 queued 部分索引；重放只按主键读取。Down12 按申请表、报告表取得锁，仅在报告与新终态都为空时回退；已有证据须前向修复，不能通过清表回退。

迁移 11 新增单行预留表，读取申请与计划沿用主键，冲突检查用单行主键，不增加队列扫描。每次接受领取产生一次插入或更新及 WAL，活预留拒绝时不重写。Down11 按节点表、预期计划表、预留表加排他锁，仅空表可回退；即使唯一预留已过期，也不丢弃记录。

迁移 10 新增预期计划表，使用申请 ID 主键/外键定位，不改历史申请和队列索引。每个首次计划写入额外产生一条主键索引和 WAL，存储取决于实际 JSON 长度；重复同计划不重写。Down10 按申请表→计划表排他锁，仅当计划表为空才可回到 9，即使已有 policy 或申请也不改动它们。已有任何计划（含取消历史）须前向修复。

迁移9新增policy和requests，不修改既有草稿、角色、提交或材料引用。Down9按凭据表→申请表→草稿表→policy锁表，遵循实际首次表访问及删除外键触发器时所需父表锁，区别于业务行锁序；仅在**申请历史及policy均为空**时允许移除。已配置、queued或cancelled都拒绝，须前向修复，不能通过清表绕过。空库Down9/重Up9保留schema8及更早的既有资料；继续回退8/7/6分别按[草稿](problem-drafts.md#入库版本与迁移)和[积压](submission-backlog.md)合同执行。

普通Docker backend负责目录/服务单测及十种合成来源布局的冻结计划对照；四包sqlc及真实临时PostgreSQL验证所有权、并发最后额度、强制policy等待后的幂等、取消竞争、撤权锁、死事务、实际丢COMMIT回包、历史摘要损坏、查询计划及非空回退拒绝。冻结集成测试真实写入对象和 PostgreSQL，在移除合成 bundle 后重新打开二者并读取冻结计划。服务与真实PG的组合测试使用合成会话观察，不等同于 Redis、浏览器、实际十题大材料或 Worker 消费验收。命令归[README](../README.md#构建与测试docker-desktop)，结果归[交付记录](delivery-log.md)。
