## 临时卷余量本地复验

2026-11-14 在 Docker Desktop Linux arm64 断网、非 root 容器中，以两个独立的 16 MiB tmpfs 模拟材料／临时目录共享卷和独立数据库卷。用 `target-inventory.py --storage-budget 5242880 5 8388608 20` 预留后续临时峰值及最低余量；只在夹具临时目录创建一个 4 MiB 文件，采集四个时点：

| 时点 | 共享卷可用字节／inode | 预检退出码 |
| --- | --- | --- |
| 写入前 | 16 MiB／61 | 0 |
| 写入后 | 12 MiB／60 | 2，字节余量不足 |
| 删除文件名但仍持有句柄 | 12 MiB／60 | 2，字节余量仍不足 |
| 关闭句柄后 | 16 MiB／61 | 0 |

独立数据库卷始终为 16 MiB／63 inode。另在新容器用同样预算创建 37 个空文件；共享卷字节余量仍为 16 MiB，但 24 个可用 inode 扣除后续峰值 5 后低于保留线 20，预检返回 2。关闭并删除一个夹具文件后可用 inode 为 25，正好满足保留线，预检返回 0。两轮只操作自建夹具，验证预检使用实际卷读数。

固定 Desktop arm64 槽（LinuxKit 7.0.14、go-judge 1.13.3、GCC 15.3.0）另连续两次通过 [真实 Worker HTTP 专项](../../README.md#http-到真实判题终态专项)。每轮用独立临时 PostgreSQL，双 API 经 mTLS 控制端得到 AC／WA／AC，已接收任务均仅有一次完成尝试。缓存条数从 0 到 1 再回到 0；观测到 `/dev/shm` 可用量从 134,217,728 降至 134,144,000 字节，少 1 个可用 inode，`/tmp` 读数不变。三笔终态读回后，同一容器仍在运行时两个临时卷的读数已回到基线；随后 Worker 排空、原槽停止。两轮日志 SHA-256：`a6f9f9664024745361001040f724ecc3d3e30e5bd7ceffd97189b3129eae3c67`。这只是固定小题的在途样本，未测持续或多槽峰值、真实试用存储配额及回收策略。

复跑将 Firefox 页面预备时间从 2 秒增至 4 秒，采样间隔仍为 600 毫秒，100 次发起最大偏差 3 毫秒。97/100 在 10 秒内完成核验，p50/p95 为 1150/2931 毫秒；失败计入排序，p99 无有限值。其余 3 次的登录开始请求收到 503，超出 1% 意外失败门槛。394 条会话响应均与上游状态一致，确认这 3 个 503 来自 API；现有报告不能区分存储异常、请求超时或密码计算准入等具体原因。证书负对照、API 退出及资源清理通过，整轮未通过。报告 SHA-256：`09236f69a85d553d46e1329f18297f955b4e297ed4e42da48cc80b766d7795de`。后续先采集脱敏的 API 错误类别及服务端耗时，再复验相同负载；不据此推断校园入口容量。

## 混合训练记录核对

服务端收件全集可用 [`training-acceptance`](../../README.md#核对-p6-混合训练记录) 按预登记窗口读取，不使用客户端已知 ID 作筛选。先停止并排空在途接收，在主库同一个只读快照导出。时间以已提交记录的 `created_at` 为准，它不是事务提交的精确时点；如果仍有在途事务，快照无法证明完整性。保留原始收件清单，用提交 ID 和受控脱敏映射核对客户端回执；未能匹配的记录保留为差异，不能从账本中删去。命令只提供收件事实，不代替验收文件所需的键映射、排队、终态和资源观测。

## 过载恢复记录核对

2026-11-14 本地训练准入预演：`python3 scripts/test-session-protocol.py --suite training-overload` 在 Docker Desktop arm64 的 2 CPU／2 GiB 夹具中，以真实普通会话 HTTPS、临时 PostgreSQL 和 Redis 运行三轮。全局额度为 2、单人额度为 1。每轮独立读到一笔运行、一笔排队；第三个账号的新键受控拒绝且查不到回执，已接收的原键仍返回同一回执。排空后同一拒绝键及一个全新键均接收，三轮累计 12 个终态均通过本人 HTTPS 详情读回。排空 4.2–6.1 毫秒，停压至新键接收 8.3–11.6 毫秒；集成 lint、race 测试及夹具退出通过。日志 SHA-256：`c39b1e6913f4a4cbd113f7dd3e45653dcb42780adc59395889735601ac38e6e5`。

这轮入队直接调用普通会话授权后的存储接口，判定由测试受控上报；毫秒数仅用于比较本地准入和回执恢复，不含真实 Worker、提交 HTTP 或现场资源峰值，也不生成下述现场账本。整阶段仍须按下列口径采集正式 HTTPS 入口和独立服务端证据。

在每轮开始前确认验收队列为空、使用固定的制品、拓扑和预登记的全局额度。通过实际同源 HTTPS 记录所有 POST（含超时）；从服务端独立导出该窗口内所有新接收提交，包含客户端未拿到回执的记录，不按客户端返回的 ID 筛选。保留原始排队快照、终态查询和资源监测记录，并确认两端时钟对齐；不能用客户端收到 202 的时间代替服务端确认接收的时间。

现场使用 `--acceptance` 提供三份原始主库清单，顺序与客户端记录一致。每份清单须精确覆盖 `[started_utc_ms, started_utc_ms + ended_ms)`（最多一小时），包括停压后的恢复探测。账本的 `accepted_ms` 以原始 `created_at` 减轮次起点、向下取整到毫秒计算。重复 ID、窗口不符或清单早于窗口结束被拒绝；清单与账本的 ID 或接收毫秒不一致时该轮失败。报告仅列差异数和清单摘要，值守人仍须独立核实压测入口、终态、资源和原始清单来源。

| 文件 | 字段 |
| --- | --- |
| 客户端顶层 | `schema: oj.p6-overload.v1`，`origin_scope: local` 或 `trial`，`release_sha256`、`topology_sha256`、`config_sha256`，原始服务端 JSON 的 `ledger_sha256`，预登记的 `global_limit`，`rounds`。 |
| 客户端每轮 | `id`、UTC 毫秒 `started_utc_ms`、相对起点的 `stopped_ms`（停止施压，允许随后做恢复探测）、`ended_ms`、`attempts`。逐次 POST 记录 `key`、`request_sha256`、`started_ms`、`finished_ms`、`status`（未收到 HTTP 响应时为 `null`）、`code`、`id`（无对应值时为 `null`）。相同键须保留相同请求指纹；键应是主体与操作范围内的原键的脱敏映射。 |
| 服务端顶层 | `schema: oj.p6-overload-ledger.v1`，相同的 `release_sha256`、`topology_sha256`、`config_sha256`；`rounds` 顺序及 ID 与客户端一致。 |
| 服务端每轮 | `id`、`saturated_ms`（独立观测队列打满的时间）、`unfinished`（排队及运行总数）、`drain_ms`（停压前已接收的提交全部终态时）、`oom_kills`、`abnormal_exits`、`peaks`（`cpu_millicores memory_bytes disk_bytes connections`）及 `ledger`。账本每笔记录 `key`、`id`、`accepted_ms`、`queued_ms`（从接收至开始判题）、`terminal_ms`、`read_ms`（通过正式入口读回终态的时点）及 `verdict`。无法观测的排空、排队耗时、终态、读回时点和判定写为 `null`。 |

同一轮的时点相对该轮起点，排队和时延为毫秒时长。拒绝用 `429 BACKLOG_LIMIT`，首次接收用 202，成功重放用 200 且 ID 一致。先观察打满，再对新键执行超限请求，并在仍满时重放已接收的键；停压后重试一笔被拒绝的原键，并用另一笔全新键验证 5 分钟内恢复正常接收。后续仍应读回两笔恢复探测的终态。三轮不得重叠；每轮最多 20,000 条请求及 20,000 笔接收记录。使用合成账号和脱敏标识，不记录源码、密码、Cookie 或凭据。

工具按轮输出接收、重放、拒绝和异常请求的时延分位数、未收到响应数、最长排队、资源峰值、排空时间和恢复时间。退出 0 表示记录满足本项检查，1 表示某轮未通过，2 表示输入无效或两份文件无法绑定。摘要只绑定留存的输入文件；仍需独立核实导出完整性、原始监测记录、实际部署条件和时钟误差。本地合成记录不能作为现场验收。
