## 混合训练记录核对

在压测前登记[发布清单摘要](../../README.md#核对同一批试用制品)、试用拓扑、受审材料版本、资源预算、冷启动及带宽条件。通过实际同源 HTTPS 采集；分别保留脱敏客户端时间线、服务端提交回读和资源监测原始证据。不要填入账号、源码、Cookie、凭据或私有地址。脚本要求一个 JSON 对象：

| 字段 | 记录方式 |
| --- | --- |
| `schema`、`origin_scope` | `oj.p6-mixed-load.v1`；隔离预演用 `local`，实际试用入口用 `trial`。 |
| `release_sha256`、`topology_sha256`、`versions` | 已登记制品与拓扑记录的 SHA-256；固定版本 ID 到 `small`、`medium`、`heaviest` 的映射。 |
| `rounds` | 三个不重叠的 15 分钟窗口；每个含 `id`、UTC 毫秒 `run_started_utc_ms`、`reads`、`submissions`、`observed_submissions`、`peaks`。 |
| `reads` | 每个合成主体在每个 10 秒窗口发起一次读。逐条记录 `subject`、`kind`（`statement`、`result` 或 `history`）、相对 `start_ms`、`elapsed_ms`、布尔 `ok`；包括失败请求。 |
| `submissions` | 每轮第 0、5、10 分钟开始后的 60 秒内，各 30 个不同主体提交。逐条记录 `key`、`subject`、`version`、`start_ms`、`confirmation_ms`、提交 `id`、`queue_ms`、`terminal_ms`、`verdict`。排队与终态时延均从提交发起时计。无接收确认则 ID 和终态字段为 `null`；已接收但无终态则后三项为 `null`。 |
| `observed_submissions`、`peaks` | 独立从服务端核对本轮全部接收记录（含客户端未知回执），逐条记录 `key`、`id`。资源峰值含 `cpu_millicores`、`memory_bytes`、`disk_bytes`、`connections`。 |

毫秒和资源数值用整数。退出 0 表示三轮记录分别满足本项门槛，1 表示至少一轮未通过，2 表示记录无效。失败或缺失样本排在有限时延后，分位落到该范围时显示 `null`；每轮同时报告有效样本数和读、提交确认错误率。WA 等正常选手判定不算系统错误。

结果只说明输入记录是否符合门槛。维护者仍须核实来源、HTTPS 路径、已审核题目、资源采样、桌面与窄屏验收，并分别保留集中登录、过载恢复和独立故障域证据。

## 过载恢复记录核对

在每轮开始前确认验收队列为空、使用固定的制品、拓扑和预登记的全局额度。通过实际同源 HTTPS 记录所有 POST（含超时）；从服务端独立导出该窗口内所有新接收提交，包含客户端未拿到回执的记录，不按客户端返回的 ID 筛选。保留原始排队快照、终态查询和资源监测记录，并确认两端时钟对齐；不能用客户端收到 202 的时间代替服务端确认接收的时间。

| 文件 | 字段 |
| --- | --- |
| 客户端顶层 | `schema: oj.p6-overload.v1`，`origin_scope: local` 或 `trial`，`release_sha256`、`topology_sha256`、`config_sha256`，原始服务端 JSON 的 `ledger_sha256`，预登记的 `global_limit`，`rounds`。 |
| 客户端每轮 | `id`、UTC 毫秒 `started_utc_ms`、相对起点的 `stopped_ms`（停止施压，允许随后做恢复探测）、`ended_ms`、`attempts`。逐次 POST 记录 `key`、`request_sha256`、`started_ms`、`finished_ms`、`status`（未收到 HTTP 响应时为 `null`）、`code`、`id`（无对应值时为 `null`）。相同键须保留相同请求指纹；键应是主体与操作范围内的原键的脱敏映射。 |
| 服务端顶层 | `schema: oj.p6-overload-ledger.v1`，相同的 `release_sha256`、`topology_sha256`、`config_sha256`；`rounds` 顺序及 ID 与客户端一致。 |
| 服务端每轮 | `id`、`saturated_ms`（独立观测队列打满的时间）、`unfinished`（排队及运行总数）、`drain_ms`（停压前已接收的提交全部终态时）、`oom_kills`、`abnormal_exits`、`peaks`（`cpu_millicores memory_bytes disk_bytes connections`）及 `ledger`。账本每笔记录 `key`、`id`、`accepted_ms`、`queued_ms`（从接收至开始判题）、`terminal_ms`、`read_ms`（通过正式入口读回终态的时点）及 `verdict`。无法观测的排空、排队耗时、终态、读回时点和判定写为 `null`。 |

同一轮的时点相对该轮起点，排队和时延为毫秒时长。拒绝用 `429 BACKLOG_LIMIT`，首次接收用 202，成功重放用 200 且 ID 一致。先观察打满，再对新键执行超限请求，并在仍满时重放已接收的键；停压后重试一笔被拒绝的原键，并用另一笔全新键验证 5 分钟内恢复正常接收。后续仍应读回两笔恢复探测的终态。三轮不得重叠；每轮最多 20,000 条请求及 20,000 笔接收记录。使用合成账号和脱敏标识，不记录源码、密码、Cookie 或凭据。

工具按轮输出接收、重放、拒绝和异常请求的时延分位数、未收到响应数、最长排队、资源峰值、排空时间和恢复时间。退出 0 表示记录满足本项检查，1 表示某轮未通过，2 表示输入无效或两份文件无法绑定。摘要只绑定留存的输入文件；仍需独立核实导出完整性、原始监测记录、实际部署条件和时钟误差。本地合成记录不能作为现场验收。
