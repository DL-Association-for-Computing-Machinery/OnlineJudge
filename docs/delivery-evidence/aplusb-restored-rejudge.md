# A+B 固定材料恢复重判

在 macOS arm64 Docker Desktop、固定断网小型参考槽和两个独立临时 PostgreSQL 14.24 容器上，使用 [A+B 租约联验](aplusb-leased-judging.md)同一份 17 点运输清单，执行 `python3 scripts/test-worker.py aplusb-restore-loop --prebuilt`（[完整参数](../../README.md#构建与测试docker-desktop)）。

| --- | --- |
| 预先固定的运输清单 | `d896b91d12727acc290e98f6cd8b0944d590efa905efaa1c84ef7cbe4a2f4a13` |
| 源库产生的备份完成清单 | `9281893f4fea7423833cb2dd9f505d51c4d846acd25fcfff4cc199e0f6eae322` |
| 合成提交的原始源码 | `e73ef41208d2b6e0fbdaaefa24eb31041daf49f44c6d2c9bbf221ef084bacd45` |

源库第一次得到 AC；同时启动的第二个 Worker 被所有权锁拒绝，现有槽的运行状态、PID 和启动时间未变。封存备份收齐 32 个不同对象、34 条判题引用；源库停止后才验证接收副本并还原。空恢复对象目录被明确拒绝；完整目录通过数据库引用及字节检查，已完成夹具的租约隔离操作零变更。

恢复库保留原提交、原键回执、源码字节、材料版本及清单摘要。第二次判题只从恢复目录取得对象，使用由操作员独立提供的同一份清单；目标库只有一条提交、两个代次各一次 AC。旧尝试的结果负载与摘要不变，新代次产生独立证据。最终用时 17.80 秒，参考槽回到 `exited`、PID 0、`none` 网络，临时数据库已清理。现有 M0 恢复专项也通过，仍得到同一提交的两次 AC。

两库在同一宿主；测试 SQL 只在隔离目标库推进代次。结果未验证正式重判入口、独立故障域、现场 SLA 或发布准入。
