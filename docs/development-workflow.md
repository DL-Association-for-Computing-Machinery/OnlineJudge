# 开发与 Git 工作流

日期：2026-10-25。状态：本次制定的项目工程规范；已配置与待启用项目见 [交付记录](delivery-log.md)。目标是需求可追踪、改动可审查、验证可复现、发布可恢复，不宣称获得任何企业认证。

## 责任与授权

- 用户是产品负责人、当前维护者及授权/发布决策者；Codex 负责授权范围的分析、实现、测试、文档、知识沉淀及满足下述条件后的 PR 合并。
- 用户于 2026-10-27 持续授权本项目的开发交付：每次执行开发计划，创建对应任务分支，完成实现与验证后整理原子提交、推送、创建/更新 PR 并核验 CI；包括本次规则治理，无需逐步重复询问。当前明确只读、暂不提交或不推送要求优先。此条替代此前“默认不提交、不推送、不建 PR”的约定，跨会话有效直到用户撤销。
- 2026-10-28 用户新增持续授权：后续 PR 在当前 head 的 CI 和 PR review 均通过后，由 Codex 直接合并，不再逐次确认。仅限本项目当前任务，不包括 GitHub 平台自动合并开关、部署发布、远端保护/秘密修改、强推或无关外部通知。当前禁止合并等明确限制优先；工具权限与审批要求保持有效。
- GitHub 操作统一使用 GitHub CLI `gh`（必要时 `gh api`）；本地 Git、fetch/push 使用 `git`。`gh` 不可用或权限不足时说明阻塞，不默认转用插件/浏览器、安装工具或提升权限。
- Codex 按下述合并门禁执行；不关闭必需检查，不用 `--no-verify`、修改 hooksPath 或降低断言绕过失败。
- 单人阶段由 Codex 完整审查 PR 并记录结论，读取并处理已有人工/自动审查反馈；AI 自审不能冒充独立人工审查或 GitHub approval。托管平台的 PR 作者不能批准自己的 PR；仓库要求的真实批准不得绕过。
- 有第二位长期维护者后，启用至少一位非作者审查；鉴权、沙箱、成绩、迁移、CI 权限等关键改动指定领域审查人。CODEOWNERS 只填核实过的真实账号，本次不伪造。

## 每个任务的闭环

1. **准备与分支**：读根规则、技术决策、相关需求、当前代码与 vault；检查工作区归属与相关 PR。明确本 PR 的一个功能或阶段、非目标、验收、风险和文档影响。新目标从更新后的主线建立 `codex/<topic>` 分支；有其他任务或未提交改动时使用独立 worktree。同一任务恢复/修复复用已有分支与 PR。
2. **设计**：涉及公共契约、数据模型、权限、任务恢复或新增依赖时先说明方案与代价；重大未决选型交用户决定。普通实现细节在授权内推进。
3. **实施**：在短期任务分支上小步修改；先复现缺陷，关键行为补回归测试。不要一次生成大量未验证模块。
4. **验证**：运行与改动相符的检查，记录命令、环境、结果和未覆盖项。应用功能必须有真实调用或端到端证据，不能只给构建截图。
5. **收尾**：审查 diff、新文件和暂存区，更新受影响文档；对已确认或实证知识执行 vault 事务、lint 和语义复核。
6. **提交与 PR**：按逻辑变更整理原子提交，正常执行 hooks，推送任务分支并使用 `gh pr create` 创建 PR；已有 PR 则更新。PR 关联需求或验收编号，列行为变化、验证、迁移/回退和限制。创建/更新前检查目标分支到 head 的完整差异，避免无关功能或前置 PR 混入。
7. **CI、审查与合并**：用 `gh pr checks`/`gh run view` 跟踪最新 head 的检查到终态，核验本地/远端分支/PR SHA 一致。审查完整目标分支差异、新文件及所有已有 review/讨论，记录结论；不能以 CI 通过替代 review。全部必需 CI 成功、相关检查无失败/待运行/未知状态、无未解决缺陷/阻断意见/讨论、所需批准满足且 GitHub 确认可合并后，执行 `gh pr merge <PR> --squash --match-head-commit <已核验SHA>`。不用 `--admin` 或 `--auto`。head 或目标分支变化后重新核验差异、审查与 CI；失败修复后重验，无法解决则报告阻塞。
8. **交付回读**：合并后回读 merged 状态、合并提交和主线，记录提交号、PR/CI/合并结果及限制，并同步交付记录与知识库。合并不是部署或业务验收；发布仍走用户独立授权。

没有 Issue 平台也可在任务描述/PR 中记录验收编号；不为流程完整而擅自创建外部工单。

## 分支、提交与合并

- `main` 为受保护集成主线；短期分支采用 `codex/<topic>`，人工分支可用 `feat/`、`fix/`、`docs/`、`chore/`。不要求长期 `develop` 分支。
- 新任务进入实现前创建对应分支，持续授权覆盖该操作；不自动切换或重置用户正在使用的工作区，可通过独立 worktree 隔离。中断恢复和同一 PR 的审查修复不另建分支。
- `codex/engineering-baseline` 仅是已合并的初始化历史，不作为长期聚合分支。新目标默认从更新后的 `origin/main` 开始。依赖未合并 PR 时明确依赖和比较基线，优先等待前置合并；确需叠加时只展示本项差异，前置合并后重新核对 base。远端配置见 [GitHub 治理](github-governance.md)。
- 一个 PR 对应一个明确功能，或开发计划中预先界定且可独立验收的阶段；阶段需明确有限范围与完成条件，不无限追加其他任务。必要测试、迁移和文档随同交付，无关目标另开分支/PR；不能仅凭原子提交数量断言 PR 范围合理。
- 一个提交对应一个逻辑变更。首行采用 `type(scope)!: summary`，scope 与 `!` 可省略；允许 `feat/fix/docs/refactor/test/chore/style/perf/build/ci/revert`，首行不超过 100 字符。
- 正文用中文写明原因、验证及限制，并沿用 `Agent-Task`、`Agent-Decision`、`Agent-Limitation`。hooks 只机械校验首行，不代替正文审查。
- 默认 squash merge，PR 标题采用同样格式；相关测试和文档与功能一起合并。共享分支不强推，已合并问题用新修复或经审查的 revert 处理。
- 本地允许检查和编辑，hooks 是提交/推送关口，不是编辑沙箱。任何直接操作 Git 对象或外部 API 都不能用来绕过项目流程。

## 本地机械约束

执行 `sh scripts/install-hooks.sh`，仅影响当前克隆，不改全局配置。安装器发现既有自定义配置或活动 hooks 时退出，先合并方案，不能覆盖。

| 入口 | 实际检查 | 不覆盖的内容 |
| --- | --- | --- |
| pre-commit | 拒绝主线/游离 HEAD 提交；检查暂存快照的路径、文件大小、私钥标记、冲突标记、空白错误和本地 Markdown 文件链接 | 业务正确性、完整秘密扫描、应用测试 |
| commit-msg | Conventional Commits 首行格式 | 提交语义、事实真实性 |
| pre-push | 检查推送目标 ref，拒绝对 main/master 的更新或删除 | 远端 API 写入、标签发布审批、完整提交历史检查 |
| repository 检查 | 当前工作树的仓库治理检查 | 隐藏/忽略文件、被跳过的外部链接、应用验收 |

pre-commit 读取暂存内容，避免“工作树已修复但暂存内容仍错误”的漏检。仓库检查不遍历 vault 或秘密文件，不输出秘密内容。文件名规则与私钥头检测只是低成本兜底，正式交付仍需专用秘密扫描。

当前脚本限制普通文件不超过 1 MiB，拒绝符号链接、私钥/证书文件名、`.env`（允许 `.env.example`）、本地配置及常见构建产物。Markdown 检查覆盖内联相对文件链接；不校验锚点、引用式链接、绝对路径和网络 URL。需要纳入大型合法资料或符号链接时先审查存储方案与例外，不能静默放宽规则。

本地 hook 可以被人为禁用，无法作为强制安全边界。远端分支保护必须阻止直接更新、强推和删除；所需配置见 [CI/CD](ci-cd.md)。本轮不添加 Codex 生命周期 hook：其信任与实际宿主触发尚未验证，根规则和已验证的 Git hooks 先承担对应约束。

自动提交/推送/PR/CI 跟踪由根规则驱动的开发流程执行，不放进 Git hook：hook 无法可靠判断功能/阶段语义、验证完成度或用户当前的只读要求，也不应在一次本地提交中隐式触发远端写入。现有 hooks 继续做机械检查，本次未增加“一个 PR 一个功能”的自动语义门禁。不得以 hook 没有自动推送为由省略上述交付步骤。

## 完成定义与例外

- 需求、代码、测试和文档状态一致；重大未决问题未被静默当成既定事实。
- 对用户已有改动保持原状；代码、文档、vault 回写和远端状态分别报告。
- 不能因检查失败而删测试、降阈值或随意增加 allowlist。例外记录原因、责任人、范围、补救与复查条件，并由用户明确批准；执行仍须遵守工具权限。
- 紧急修复也保留任务分支、最小回归验证、人工决策和事后记录。比赛期间原则上冻结常规发布。

## 知识编译与持续改进

沿用项目已适配的 Karpathy 式方法：原始证据 → 有来源的规范页 → 项目使用 → 验证产出回流。不是将 AI 答复反复总结成“已验证事实”。

先检索与哈希去重，区分用户确认、工程建议、静态分析和运行证据；原始资料只增不改；知识页以链接指向仓库规范，避免维护两份全文。用单一可恢复事务更新主题、来源/断言账本、索引、热点、日志与项目进度，随后结构 lint 和单独语义复核。没有新知识不制造笔记；不保存整段聊天或秘密。
