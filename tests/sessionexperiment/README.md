## 凭据原子轮换与原期限保持（2026-10-31）

`codex/session-token-rotation` 从成功 fetch 后的 `bc0c138` 创建。新增受信 `POST /rotate-fixture` 和屏障探针；仍只在 `_test.go`，不提供正式登录、权限提升或 CSRF 接口。普通、保持登录和管理均维持原 scope、载荷、Cookie 持久策略及登录起绝对 deadline；轮换作为显式活动可刷新空闲期限，但不能延长绝对期限或接受查询参数升级策略。

- [SCS v2.9.0 RenewToken](https://github.com/alexedwards/scs/blob/v2.9.0/data.go) 默认先删除旧记录并重置期限，不能直接满足本实验约束。仅在当前 manager 副本上安装 `rotationStore`：Load 冻结服务端旧载荷，Delete 只暂存一次精确删除意图，SCS 产生新随机凭据后用 `SetDeadline` 恢复原期限，Commit 仅允许一次且解码校验载荷/期限未变。Gob map 重编码可能顺序不同，语义比较不要求字节编码相同；Lua 则用被冻结的原始字节核对当前旧记录，其他请求更新过旧载荷时可返回 409。
- 既有 PostgreSQL 全局行→账号行的锁序及双代次校验保持。单个声明 `#!lua` 的脚本在首条写之前核验旧记录类型/身份/载荷/有效期限、物理到期点、旧名额分数、索引类型/期限/活跃名额数及新键不存在；成功时写新记录、旧记录删载荷留原期限墓碑，原子移交同一个名额。索引最大分数同时受命名空间业务上界限制：个人 7 天、管理 8 小时；普通 12 小时会话可以和 24 小时空闲的保持登录会话共用索引。它检查当前来源和索引，不宣称逐一验证全部兄弟记录。
- 三种 profile 均在三名额满时一换一，旧凭据在两 API 拒绝，新凭据/其他会话可读，完整快照仅允许新记录、旧墓碑及准确的索引成员/期限交换。每种 profile 的 12 个已加载轮换与 24 个新登录竞争，恰好一个轮换成功，其余轮换拒绝、新登录全冲突。旧请求迟到保存不能复活；已加载轮换跨退出、账号代次/恢复代次变化、闭门及空闲/绝对到期均拒绝，不创建候选。
- 连接池取池失败及真实 noeviction 入口 OOM 返回有界 503、无原始 Set-Cookie，载荷/索引/绝对期限不变，旧会话恢复可用。畸形索引类型/分数/期限、超额名额、旧载荷变化、新键碰撞、策略/期限篡改及重复提交均在写前拒绝；畸形状态用完整类型/逻辑内容和原始 int64 绝对过期值比较，不把非规范 DUMP 字节编码当成逻辑状态。
- 真实写入后在应用适配器层丢弃回执，HTTP 503/无 Cookie，旧凭据已失效、新凭据只占原来一个名额；测试进程持有的冻结候选可用既有原语核验。不会自动重试、发 Cookie 或重新生成候选；正式跨请求的轮换结果核验/放弃、持久化尝试、崩溃恢复仍未提供。

本项没有新依赖、生产程序、SQL、迁移或驱动改动，回退新增探针/适配器即可。仅同进程双 TLS API 和预认证身份，未验证真实权限提升、重认证、跨进程/主机或浏览器/Gin/CSRF。声明脚本只拒绝已超限入口，不保证执行中 OOM 或其他 Redis 运行错误能回滚；失败复现、修复与实测见[交付记录](../../docs/delivery-log.md)。完整 AC23/M0 未通过、未部署。

## Redis 服务端断连后的重连预算（2026-10-30）

`codex/session-reconnect-budget` 从成功 fetch 后的 `1545a60` 创建。本项沿用每 API 主池上限 8、共享 pipeline 池和无自动重试配置，只新增测试，不改变生产程序或实验存储协议。

- 两个 TLS API 的个人保持登录和管理会话共用各自的 Redis 客户端。先借住并初始化真实 8+8 条连接，再归还池；observer 按精确随机 ClientName 提取正整数 ID，仅执行 [CLIENT KILL ID](https://redis.io/docs/latest/commands/client-kill/) 定向断开，每次必须返回 1。请求放行前确认两个 API 均为零条连接，observer ID 与 Redis run_id 保持不变。
- 连续两轮各断开 16 条连接，每轮 32 个并发工作者共执行 128 次跨 API/双 scope 的只读请求。无重试配置下允许 200 或有界 503，均不得发 Set-Cookie、不得误报 401；随后四种 API/scope 组合必须读取 200。请求放行前、执行中及每次完成后采样 CLIENT LIST，检查已初始化并带 API 标签的连接各不超过 8、旧 ID 不再出现；恢复后再次实际借满 8+8，核验全部为新 ID。离散采样只证明观察到的计数，不保证捕获每一个瞬时峰值或尚未设置标签的连接。
- 两轮只读前后完整载荷、键集合、名额索引/分数和绝对到期时刻均不变；恢复后的活动保留原绝对期限，跨 API 退出后旧凭证被拒绝，各 scope 重新准确接纳三名额、第四次冲突。另对个人和管理各验证一次：请求已加载后在另一 API 撤销，断开连接并确认重连完成，最后放行迟到保存，必须 401/无 Set-Cookie，撤销后快照不变，其他有效会话继续可读。

仅同进程双 API、已建立且空闲的连接被服务端关闭；Redis 数据/进程持续存在，未模拟网络分区、服务重启、在途写入丢回执、跨进程/主机或生产重新登录峰值。观察客户端和未覆盖的 PubSub/AutoPipeline/维护连接不计入 API 预算；本项没有生产容量结论。没有新依赖、SQL、迁移或驱动改动，回退新增测试即可；实测见[交付日志](../../docs/delivery-log.md)。完整 M0 未通过、未部署。

## Redis 连接预算、饱和与恢复（2026-10-30）

`codex/session-pool-budget` 从成功 fetch 后的 `ff6b4a9` 创建。每个实验 API 的共享 Redis 客户端现在明确设置 `PoolSize=8`、`MaxActiveConns=8`，并用 `PipelinePoolSize=-1` 禁用独立 pipeline 池，使普通命令和本实验 pipeline 共用主池。仍禁用自动重试，保留 1 秒连接/读/写/取池超时及 3 秒 HTTP 上下文；每个客户端有独立随机观测标签，不包含会话凭据。

- 先占住真实初始化的主池连接，再执行 PING pipeline：原配置可通过额外 pipeline 池成功执行，修复后明确取池失败，释放后同一路径可用。锁定版本中 pipeline 池不受主池 `MaxActiveConns` 额度约束，不能只设置后者；依据见 [go-redis v9.23.0 配置源码](https://github.com/redis/go-redis/blob/v9.23.0/options.go)。
- 同进程两个 TLS API 各持有 8 条连接，用独立观察客户端读取 Redis `CLIENT LIST`、按精确标签分组，实际观察合计 16 条。16 个跨 API/个人及管理 scope 的读取、活动、退出和新登录请求并发执行；持有期间实时采样连接数，均在 4 秒验证预算内返回 503、无 Cookie，全载荷、索引及绝对到期时刻不变。释放后原会话可读、退出/撤销生效、名额恢复。
- 屏障先确认已加载会话，再占满一个 API 的池：该副本保存失败、无 Cookie/状态改写，另一 API 仍可读取；释放后可续期且保留原绝对期限。两种 scope 均有独立用例；失败路径也归还持有连接并释放屏障。
- 压力观测沿用的旧快照辅助函数在负向运行中暴露 `KEYS → 内容 → PEXPIRETIME` 自然到期竞态。现在单次 `EvalRO` 原子读取、以嵌套 RESP 保留二进制载荷，对有效键严格检查 TTL/类型；仅排除按 Redis TIME 已自然到期的正期限项。新增同截止时间 hash/index 的实时过期观察，以及缺失 TTL/错误类型拒绝且不改写记录的验证。它只扫描私有 standalone 夹具前缀，不能作为生产/Cluster 扫描方案；[Redis 脚本原子与只读/OOM 语义](https://redis.io/docs/latest/develop/programmability/)是机制依据，行为仍以实际实验为准。

16 条仅指本实验两个 API 普通命令/共用主池 pipeline 路径的连接，不含观察客户端另 1 条、驱动或其他客户端，也未覆盖 PubSub、AutoPipeline、维护通知等其他路径；不是整个 Redis 服务或进程所有可能用法的全局连接上限。8 是实验参数，生产额度、跨进程/主机、吞吐、RSS/CPU、数据库连接及重连峰值仍待验收。无新依赖、SQL、迁移、驱动或生产入口；回退本项测试配置即可。实际验证和失败记录见[交付日志](../../docs/delivery-log.md)，完整 M0 未通过、未部署。

## 管理会话期限与 scope 隔离（2026-10-30）

`codex/session-admin-lifetime` 从成功 fetch 后的 `2485f9f` 创建。两个现有 TLS API 各自增加启动前配置的管理 manager 和存储适配器，使用独立 `admin_session` Cookie、`/admin-fixture` Cookie Path、`admin:` Redis 子命名空间；同一 API 的两个 scope 共用一个配置 `PoolSize=8` 的 Redis 客户端和 PostgreSQL 账号/恢复代次。管理登录仍是预认证测试身份，**不验证真实管理资格、密码或敏感操作再次验证**，不接入生产。

## 普通会话空闲与绝对期限（2026-10-30）

`codex/session-lifetime` 从成功 fetch 后的 `4a62b15` 创建。本项只扩展测试处理器：已认证的 `POST /activity-fixture` 作为受信活动探针，调用原 SCS `Commit`；`GET /me` 继续只读，GET 活动探针返回 405。默认普通会话仍为空闲 2 小时、绝对 12 小时；用例启动前同时缩短两 API 的配置，用真实墙钟验证时间流逝，不改 Redis TIME 或篡改到期字段。

- 2 秒空闲、6 秒绝对期限下，多次跨副本后台读取均成功且不发 Cookie，完整载荷、名额分数和绝对到期时间不变。原空闲时刻后，两副本读取/活动均 401 且无 Cookie；token 记录保留到原绝对期限，单会话索引自然到期。重新登录恰好接纳三个会话，第四个冲突。
- 显式活动延长空闲期限，同一凭据成功跨越原空闲边界；每次读取 Redis 期限，核对原绝对 deadline 不变、空闲 expiry 不倒退且不超过它、单名额分数及索引 TTL 等于 expiry、token TTL 等于 deadline。持续活动最终准确截断到原 deadline，随后两副本均拒绝旧会话/活动，载荷与索引自然消失、新名额仍为三个。GET 活动探针无续期副作用。
- 屏障确认请求已加载会话，再等待 Redis 时钟跨过空闲或绝对期限，最后放行保存；两种情况均 401 且不发 Cookie，拒绝前后保留记录/期限/索引完全不变，旧会话不能复活或额外占位。1 秒到期边界低于处理器 3 秒超时，避免把超时 503 冒充过期拒绝。

Docker Desktop Linux arm64、Go 1.26.10、Redis 7.2.4、PostgreSQL 14.24：原三十项行为/race 基线通过（20.828 秒）；最终三十四项通过（30.829 秒，另含二十六个子用例），格式、模块校验、vet 通过，静态检查零问题。Astra 针对性复核与主代理实测/完整差异自审不代替独立人工审批。未增加依赖、SQL、驱动或生产端点，回退新增测试与活动探针即可。交付状态见[交付日志](../../docs/delivery-log.md)。

这是同进程双 TLS API 的普通期限子实验，没有定义浏览器活动识别、续期采样/限频或到期提醒协议；不是正式 Gin/CSRF 中间件，也没有验证“保持登录”、管理/参赛期限、凭据轮换保留登录起点或独立 API 进程的期限行为。缩短时钟与默认配置断言不等于真实等待 2/12 小时；完整 AC23/M0 仍未验收、未部署。

## 数据库逻辑回档与新恢复标识（2026-10-30）

`codex/session-database-restore` 从成功 fetch 后的 `2fba7cf` 创建。真实 `pg_dump`/`pg_restore` 先复现旧全局整数代次的问题：备份为 1，曾使用 2、随后用 3 废止它；回档到 1 后再递增会重复使用 2。Redis 中保留的历史会话因此重新返回 200，历史恢复完成操作也能误开入口。不能把“从备份值加一”视为从未使用过的新代次。

## 独立 API 进程与重启（2026-10-29）

`codex/session-process-recovery` 从成功 fetch 后的主线 `e424392` 创建，唯一目标是补齐进程边界验证。复用原有测试处理器和存储适配器，通过同一 race 测试二进制启动两个子进程，各有一个 TLS HTTP server、SCS manager 和 Redis 连接池；PID 与父进程、另一 API 均不同。父进程只信任子进程经管道传回的测试证书，没有关闭 TLS 校验；管道屏障不作为 HTTP 端点暴露。

- 24 个并发请求分发到两个进程，恰好 3 个成功、21 个冲突；失败不发送 Cookie，成功会话在两个进程均可读取。
- 管道确认 A 已加载旧会话，再由 B 完成撤销，随后释放 A 保存：返回 401 且不发 Cookie。
- 对执行撤销的 B 发送 SIGKILL 并等待退出，断言退出信号；A 继续拒绝旧会话、接受有效会话。使用相同 Redis 命名空间启动新的 B 后，两进程仍拒绝旧会话、接受另外两个有效会话；恰好能补一个名额，之后两端均拒绝超额登录。
- 正常子进程关闭控制管道后退出并回收；子进程设置 race 首错立即退出，并检查退出状态。强制结束只用于上述故障注入。

Docker Desktop Linux arm64、Go 1.26.10、Redis 7.2.4 下，既有六项基线通过（1.306 秒）；新增后完整七项行为测试及 race 通过（3.405 秒），其中进程用例 2.08 秒，gofmt、go mod verify、vet 同时通过。`TestSessionAPIProcess` 是子进程入口，父进程扫描时跳过，实际由进程用例执行。命令仍为下方 `scripts/test-session.py`，无需新依赖或镜像。

Redis 在整个用例中持续存活，未恢复快照；这只证明 API 进程丢失内存不影响 Redis 中的会话状态，不证明 Redis 宕机/持久化、旧快照恢复、认证代次、跨主机高可用或生产准入。下一项是认证代次与 Redis 故障/旧快照恢复验证，完整 AC23/M0 仍未通过。

## 原名额与撤销子项（同进程基线）

- SCS v2.9.0、go-redis v9.23.0、Go 1.26.10；真实 Redis 7.2.4，Docker Desktop Linux arm64。
- 两个独立 SCS manager、Redis 连接池及 TLS HTTP server，共处一个 Go 测试进程。不是两个 API 进程、跨主机或 Gin 中间件验证。
- 24 个并发请求分发到两个 API，恰好 3 个成功、21 个冲突；失败不发送 Cookie。两个 API 都能读取成功会话，撤销后都拒绝旧 Cookie，并释放一个名额。
- 屏障确保 API A 已加载旧会话，API B 撤销完成后才允许 A 保存；A 被拒绝，不能复活旧凭证或重新占位。
- 撤销凭证即使改换主体也不能保存；失败不占用原主体或新主体的名额，两者仍各可接纳三个会话。
- 空闲过期拒绝迟到续期并释放名额；同一凭证重复保存仍只占一个名额；绝对期限不可修改，过期绝对期限不能创建会话。
- 关闭一个 Redis 客户端连接池模拟访问不可用：返回 503，不清除 Cookie，不冒充服务端退出成功；另一个 API 仍能访问原会话。不是 Redis 服务宕机、网络超时或内存不足演练。
- Cookie 验证 Secure、HttpOnly、SameSite=Strict；Redis 键只含凭证 SHA-256 摘要。公开 HTTP 面、日志扫描和浏览器行为未验收。

本次 `gofmt`、`go mod verify`、`go vet`、六项 `go test -race -count=1` 全通过（测试进程报告 1.311 秒），迁入后的五项基线也通过（1.307 秒）。旧实验曾发现 Redis Cmd 接口误用与客户端 Timeout 并发修改，迁入版已修正；不将旧失败算作本次复现。

## 机制与限制

Redis Lua 将名额检查与保存串行执行；按主体的有序集合索引释放已到期名额，无全库扫描。撤销仅删除载荷，不立即删除记录，记录保留至绝对期限，拒绝后续保存；若直接删除整条记录，存储无法区分迟到保存与新会话。代价是普通会话撤销/过期元数据最多保留 12 小时，保持登录最多 7 天，管理最多 8 小时；本次未进行内存容量测试。

时间判定使用 Redis TIME；SCS 生成绝对期限及有效载荷，适配器按服务端 scope/载荷接受 12 小时内普通会话、7 天内保持登录或 8 小时内管理会话。读请求手动 Load，不自动 Commit；本实验未验证正式有效活动采样或 SCS LoadAndSave 与 Gin 的生命周期。账号为固定、预认证测试主体；原有用例没有账号检查，新增代次用例通过可选 PostgreSQL 夹具核验，仍无密码、正式账号数据库或当前资源权限。

Lua 的串行性不等于运行时错误回滚；入口超限拒绝已有上述证据，脚本执行中越限/其他运行错误、OOM kill、凭证轮换、比赛会话、真实管理授权/重认证、CSRF、PostgreSQL 会话对比和负载均未完成。全局代次/旧 RDB 与独立 API 进程重启的有限证据见上文，不能将此适配器直接用于生产，也不代表 AC23 或完整 M0 通过。

## 复现

测试驱动仅使用本机已存在的工具镜像与 Redis 夹具镜像，不自动拉取：

- `oj-toolchain:local`：本仓库 Dockerfile 的 `toolchain` target；可用 `docker --context desktop-linux build --target toolchain -t oj-toolchain:local .` 构建，首次需正常网络/证书信任。
- 固定 Redis 镜像 ID `sha256:92dbfb0bc408385074c83eb3a868b5f273d425f079f2af808403d22dcd94b667`，本机 `redis/redis-stack-server:7.2.0-v9` 缓存。只启动其中 redis-server，不加载 Stack 模块。这是本机旧夹具，不是可移植镜像分发或生产版本准入。

其他机器可通过 `--redis-image <已有镜像引用>` 指定已准备的 Redis 镜像；驱动先检查本地存在，绝不自动拉取。更换版本需记录版本并重新验证，不能沿用本页结论。

容器内访问 Go 代理出现 `x509: certificate signed by unknown authority`。此次用宿主正常 TLS 与 `sum.golang.org` 校验下载到独立临时缓存，构建/测试仍在 Docker 中；没有关闭证书或模块校验。具备宿主 Go 下载能力时，在本目录执行：

```sh
GOPROXY=https://proxy.golang.org GOSUMDB=sum.golang.org GOMODCACHE=/private/tmp/oj-session-mod go mod download all
```

回到仓库根目录执行实际验证入口：

```sh
python3 scripts/test-session.py --module-cache /private/tmp/oj-session-mod
```

驱动创建随机命名的 internal 网络及两个一次性 Redis：原夹具保持 tmpfs，恢复夹具仅挂载本次新建的私有临时目录保存 RDB。无宿主端口、用户数据库或 Docker socket 挂载；有限轮询就绪，测试执行预算 300 秒，各恢复命令另有超时。测试容器只读挂载实验源码/缓存，`GOPROXY=off`，`run.sh` 创建私有 PostgreSQL 后校验模块并运行 vet/race。恢复请求使用一次性随机 nonce，驱动只执行固定的本次容器 kill/start，再写入固定完成标记；测试输出不能指定容器、宿主路径或命令。正常完成或命令失败后清理本次容器、网络及 RDB 临时目录，不操作既有 volume；强制终止宿主驱动后的残留清理未验收。

RDB 是时点快照，恢复可能回退其后的退出/撤销，原理见 [Redis 持久化说明](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)。本实验用外部 PostgreSQL 代次拒绝恢复后的旧数据，不把 RDB 本身视为撤销连续性的保证。
